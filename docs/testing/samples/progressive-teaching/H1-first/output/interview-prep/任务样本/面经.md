# 面经：任务样本

> 以下为目标简历与学习口播，供掌握后选用。分析范围：后端方向，合成教学项目的 `task.py` 全部 27 行；没有个人经历或性能指标材料。

## 项目简介（简历可用）

基于 Python 的同步任务执行教学程序，将任务状态记录与外部处理函数分开，支持成功结果交付和针对指定异常的有限重试。

## 简历 bullet

- **同步任务执行与状态归属：** 由任务对象保存状态、累计尝试次数与结果，执行层同步调用外部传入的处理函数；每次调用前记录运行态和尝试次数，正常返回后保存结果、标记完成并返回同一任务对象。
- **有限重试与异常分流：** 按任务累计尝试次数与总上限控制执行预算，捕获处理函数的 `ValueError` 后标记失败，次数未用尽时继续尝试；成功立即返回，次数耗尽返回任务对象，其他异常向调用者传播。

## 面试问题

### Q1 同步执行如何记录状态并交付结果

- 对应支柱：B1
- 触发依据：B1 中“任务对象保存状态、累计尝试次数与结果”“同步调用外部传入的处理函数”。
- 考查目标：解释数据归属、执行职责、同步返回与对象共享的实际含义。
- 学习入口：[C01 同步执行与任务状态](../guide-backend/01-同步执行与任务状态.md)；重复调用边界见 [C02](../guide-backend/02-有限重试与异常边界.md)。

**面试官问题**：同步执行时，任务状态由谁维护，成功结果怎样交给调用方？

**口播版**：我会把数据和执行职责分开看。任务对象保存标识、状态、累计尝试次数和结果；执行层负责推进这些字段，具体业务交给传入的处理函数。一次正常调用会先把任务设为运行中并增加尝试次数，再把任务标识交给处理函数。处理函数在当前调用栈中返回字符串后，执行层保存结果、标记完成，并返回调用方传入的同一个对象。因此调用者既能读到最终状态，也能取得结果。这里没有后台消费者或异步受理，函数没有结束之前调用方就仍在等待。把处理函数作为参数，是为了让业务动作与执行流程分开；它不会自动带来线程隔离、超时控制或持久化。

**追问 1**：你说返回同一个对象，这会给调用方带来什么影响？

**触发依据**：主回答中的“返回调用方传入的同一个对象”。

**口播版**：我会把它当作原地更新接口使用。持有同一对象引用的代码能看到状态和次数变化，无须用返回值替换旧对象。代价是异常传播时，已经写入的字段也会保留，不会自动回滚。如果多处代码能同时修改它，当前实现没有锁或版本检查，无法保证状态转换一致。若需要并发执行，要先确定状态写入的唯一责任方，再设计互斥或持久化条件更新；这属于后续设计。

**追问 2**：你提到已经写入的字段不会回滚，如果任务已经完成，再交给执行层会直接返回吗？

**触发依据**：上一回答中的“原地更新接口”“状态和次数变化”；B1 中的“累计尝试次数”。

**口播版**：不会仅凭完成状态直接返回。当前执行入口检查的是累计尝试次数是否低于上限，没有完成态短路。若第一次成功只用了默认两次预算中的一次，再传入同一个对象且上限不变，处理函数还会被调用一次，结果可能被覆盖。这说明状态记录与执行准入是两回事。若要让完成任务重复提交时复用结果，需要增加明确的终态规则，并结合处理函数的副作用决定是否需要幂等记录；当前源码没有实现这层保证。

### Q2 有限重试如何决定继续与停止

- 对应支柱：B2
- 触发依据：B2 中“累计尝试次数与总上限”“捕获处理函数的 ValueError 后标记失败”“其他异常向调用者传播”。
- 考查目标：解释预算计数、正常与异常出口，区分有限重试、超时及幂等保证。
- 学习入口：[C02 有限重试与异常边界](../guide-backend/02-有限重试与异常边界.md)。

**面试官问题**：有限重试如何决定继续与停止，异常类型又如何改变行为？

**口播版**：我会先说明这里的上限是总尝试次数，包含第一次调用。默认上限为二，新任务初始计数为零，每次调用处理函数前先把计数加一。如果处理函数抛出 `ValueError`，执行层只把状态标成失败；下一轮能否继续，仍由累计计数与上限的比较决定。例如第一次失败、第二次成功，最终是完成态且次数为二；连续失败两次，则返回失败任务。正常返回会立即结束循环，其他异常则直接向调用者传播。这个边界简单，但它把所有 `ValueError` 都当作可继续尝试的错误，没有依据业务语义细分，次数限制也不能保证单次调用能及时返回。

**追问 1**：你说其他异常会传播，任务对象会是什么状态？

**触发依据**：主回答中的“其他异常则直接向调用者传播”。

**口播版**：在处理函数开始前，状态已经写成运行中，次数也已经增加。若它抛出未捕获的异常，完成态和失败态分支都不会执行，调用者会收到异常，而对象保留运行态和增加后的次数。它不能被解释成后台仍在运行。当前没有统一收口状态的逻辑，如果要演进，我会先定义未预期异常应该记录成什么状态，再决定是否重新抛出，并保留原异常，避免把错误静默吞掉。

**追问 2**：你提到没有细分业务错误，若处理函数先完成部分写入再抛出 `ValueError`，继续尝试会有什么风险？

**触发依据**：主回答中的“把所有 ValueError 都当作可继续尝试的错误”。

**口播版**：第二次会用相同任务标识再次调用处理函数，已经发生的副作用可能重复。次数上限只限制重复多少次，没有消除重复；传入相同标识也不等于已经实现幂等。我会先确认哪些错误确实可重试，再根据业务存储选用唯一约束、已处理记录或事务内结果复用。若操作无法安全重放，就不能直接套用当前重试分支。这些方案尚未实现，不能把教学程序写成可靠消息消费系统。

**追问 3**：你说次数上限不保证及时返回，原因是什么？

**触发依据**：主回答中的“次数限制也不能保证单次调用能及时返回”。

**口播版**：循环只有在处理函数返回或抛出异常后才有机会检查下一轮。若某次调用一直阻塞，剩余次数不会减少到终点，调用者也一直等着。当前没有超时、取消或退避。若未来处理函数访问网络，我会先在具体 I/O 层设置超时，再考虑总执行期限和可取消的执行模型；不能只给循环再加一个次数判断，就声称有了超时控制。
