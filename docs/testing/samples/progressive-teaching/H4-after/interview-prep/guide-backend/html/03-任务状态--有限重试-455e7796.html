失败的是这次尝试，
任务身份仍然是 T-17。

调用者把一个 Task 对象交给 run_task。第一次调用 handle 抛出 ValueError 后，函数还没有返回；只要次数未耗尽，循环就会用这个对象的同一个 id 再调用一次。

为什么失败后还是同一任务？因为代码只把 task.status 改成 failed，没有创建新的 Task，也没有修改 task.id。failed 是这个对象当前的状态，不是“换一个任务”的命令。

下一轮仍操作参数 task 指向的对象，把它改回 running 并增加 attempts。只有成功返回，或预算用尽走到循环外的 return task，这次 run_task 调用才结束。

1. 先把“任务”与“尝试”分开

以调用者先创建 task = Task("T-17")、再调用 run_task(task, handle) 为例：任务是要完成的这件事；尝试是为完成它而进行的一次 handle 调用。这个例子使用默认总预算 max_attempts=2，因此最多调用两次，不是首次调用之外再重试两次。

身份 · id

T-17 → T-17

两次执行都从同一个对象读取 task.id，所以传入 handle 的字符串相同。

已消耗次数 · attempts

0 → 1 → 2

每次调用 handle 前加一。第一次失败仍占用一次预算，第二次是剩下的最后一次。

这些字段都属于同一个 Task。run_task 原地修改对象；handle 收到的只是它的 ID 字符串，不是一个新任务对象。保持同一身份来自这段实现的选择，并不是所有重试系统都天然如此。

2. 关键在于 except 后没有 return

下面保留 task.py 第 14–27 行 的实际执行结构。while 每轮先检查预算；捕获异常后沿代码顺序走到循环体末尾，再回到条件判断。

def run_task(task: Task, handle: Callable[[str], str], max_attempts: int = 2) -> Task:
    if max_attempts < 1:
        raise ValueError("max_attempts must be positive")
    while task.attempts < max_attempts:
        task.status = "running"
        task.attempts += 1
        try:
            task.result = handle(task.id)
        except ValueError:
            task.status = "failed"
        else:
            task.status = "done"
            return task
    return task
  1. 允许进入：0 < 2 成立。对象从 queued 变为 running，attempts 变成 1，然后调用 handle("T-17")。
  2. 第一次失败：ValueError 被捕获，只执行 task.status = "failed"。异常路径跳过 else，因此没有执行其中的 return task。
  3. 再判断：走到循环末尾，检查 1 < 2。条件成立，所以再次运行同一个循环体；参数 task 仍指向原来的对象。
  4. 第二次调用：状态改为 running，次数变成 2，继续调用 handle("T-17")。没有任何语句让 ID 变成别的值。

failed 本身不决定退出。退出由成功分支的 return，或次数条件不再成立决定。这个同步函数里没有消息重新入队；下一轮调用直接发生在同一个循环中。

3. 同一个 failed，可以出现于两个时刻

第一次失败后，预算还够

queued → running（1）→ failed（1）→ running（2）→ done（2）

第一次的 failed 是函数内部经过的状态；随后 1 < 2 成立。第二次成功，结果写入同一个对象的 result，状态设成 done 并返回。括号表示已用次数，ID 全程是 T-17。

第二次也失败，预算已经用完

queued → running（1）→ failed（1）→ running（2）→ failed（2）→ 返回

捕获第二次 ValueError 后，2 < 2 不成立，跳出循环。循环外没有重新改状态，所以返回的还是原对象，status="failed"、attempts=2。这是这次调用结束时的失败状态。

两次都抛出 ValueError 时的字段对照（新 Task，总预算 max_attempts=2）
时刻任务 ID状态 status已用次数 attempts
初始：调用前T-17queued0
第一次失败：捕获后T-17failed1
最终失败：返回时T-17failed2

三个时刻是同一个 Task 对象。第一次失败后还剩一次预算，会再次进入 running；最终失败后预算耗尽，本次 run_task 调用返回。

第一次就成功，立即返回

queued → running（1）→ done（1）→ 返回

没有抛异常才进入 else。这里直接 return task，所以即使还剩一次预算，也不会再执行成功任务。

5. 保留 ID 能说明什么

能说明：同一个 Task 的处理被再次尝试，attempts 延续累计；这段实现没有靠创建新对象来重新获得次数预算。

不能说明：第二次调用一定安全。如果 handle 在抛错前已经产生副作用，再传相同 ID 也可能重复产生副作用。样本没有利用 ID 做幂等检查；相同 ID 与幂等是两回事。

  • 本页例子从 attempts=0 开始。若调用者传入的对象已有尝试次数，while 使用已有计数，函数不会重置预算。
  • 只有 handle 抛出的 ValueError 会走这条重试路径。其他异常会向外传播，不能概括成“任何失败都重试”。
  • 代码没有等待或退避，第一次失败后马上回到循环条件；没有外部队列、持久化或并发控制，也没有重启后恢复任务的实现。

需要懂什么、记住什么

懂因果：异常分支改的是状态，既没有创建任务，也没有结束函数；还有预算就回到循环，用原对象的 ID 再调用一次。是否还是同一个任务，要看对象与 ID 的流向，不能只看状态名称。

记流程：检查预算 → running → 次数加一 → handle(同一 ID) → 成功则 done 并返回；ValueError 则 failed，再检查预算。耗尽时从循环外返回，保留 failed。

回到 Q1：同一任务与多次尝试 时，可以直接沿这条因果解释。若继续追问，最相关的下一点是：“相同 ID 为什么仍可能重复产生副作用？”
