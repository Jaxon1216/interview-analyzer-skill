C04 · 断线后，下一条事件从哪里开始？

一次运行已经发过五条事件。浏览器重连时，内存桥能补发多少，取决于最后收到的事件 ID 和服务器仍保留的窗口。

机制怎么工作

每个 run 各有一份内存事件日志。每次发布按「毫秒时间戳-本次运行的序号」生成 ID。超过容量时删除最早的数据，并把 start_offset 推到仍保留的第一条。客户端把最后收到的 ID 放进 Last-Event-ID，服务端据此定位下一条。

下面是内存桥选起点的两个判断。序号低于窗口下界时，服务器已经无法核对当时的完整 ID，于是报告缺口。序号落在窗口内时，还要核对完整 ID 才能跳过那一条。订阅期间窗口也可能前移；若待读位置落到窗口外，桥同样发出缺口。

if seq < stream.start_offset:
    return self._make_gap(stream, last_event_id)
local_index = seq - stream.start_offset
if 0 <= local_index < len(stream.events) and stream.events[local_index].id == last_event_id:
    return stream.start_offset + local_index + 1
切换重连请求

示意数据 · 同一 run，容量设为 3，已经发布序号 0 到 4。划线的是已淘汰的两条，实线的是可回放的三条。切换请求时，服务端窗口保持相同。

1000-01001-11002-21003-31004-4

收到过 1003-3，下一条是 1004-4

Last-Event-ID = 1003-3 → seq = 3 → 窗口索引 1 → 从序号 4 发起回放

此刻可收到1004-4

桥用 3 − 2 得到本地索引 1，再比对该槽位里的完整 ID。两者相同，订阅从命中事件之后开始。当前只补到 1004-4；若 run 仍在运行，订阅继续等新事件。

收到过 1001-1，第一条是 gap

Last-Event-ID = 1001-1 → seq = 1 → 1 < 2 → StreamGap

此刻可收到gap · stream_replay_gap

此时网关直接发送 gap 帧，不发送窗口里的 1002-2 至 1004-4。载荷给出最早 ID 1002-2、最新 ID 1004-4，以及恢复指令 reload_durable_state。gap 帧省略 SSE 的 id 字段，随后结束这条订阅。

传入 9999-3，从 1002-2 开始

Last-Event-ID = 9999-3 → seq = 3 → 窗口索引 1 → 完整 ID 不匹配

此刻可收到1002-2 → 1003-3 → 1004-4

窗口索引 1 中存着 1003-3。调用方给的 ID 序号相同，但时间部分不同，桥会记录警告，从当前保留的最早一条开始。格式无法解析的值也走这个回退分支。若能解析且序号低于 2，则走左侧的已淘汰分支，即使时间部分无从核对。

省略请求头，从 1002-2 开始

未携带 Last-Event-ID → 起始位置 = start_offset = 2

此刻可收到1002-2 → 1003-3 → 1004-4

调用方没有指定上次收到的事件，桥直接从仍保留的窗口头部订阅，无需匹配 ID，也不会记录未知游标警告。序号 0、1 在这个快照中已经被删去。

记住这一点

能定位最后一条，就从它的下一条接着读；能判定游标过旧，就用 gap 提示重载持久状态；其余未知游标在内存实现中从窗口头开始。gap 只结束当前订阅，运行可以继续。真正的流结束另发 end；创建连接的断线取消还需要满足独立的策略和运行状态条件。
