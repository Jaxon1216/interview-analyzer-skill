# HTML 怎样真正教会一个机制

HTML 是一节短课。它应让读者获得一个可用的判断方法，而不是把完整课文、状态枚举和源码索引重新排版。沿用 teach 的单一学习成果、匹配已有知识、工作示例与即时反馈；不机械创建整套教学工作区，也不默认布置作业。

## 先设计，再实现

委派前说清：读者已知什么、本页唯一主要未知是什么、常见误解、一个具体学习成果、支撑它的源码位置。例如“能判断两个执行共享 client 时，第一方结束为何不能释放、最后一方结束为何可以”。这比“讲解租约机制”更能约束选材。

用同一个具体实例从起点走到核心结局。先给必要结论，再带着读者观察结论怎样产生。初始界面只呈现建立主模型所必需的概念；兼容分支、罕见失败与配置例外在主模型之后补充。不要一开始摆五六个答案页让读者自己组织因果。

每个操作推进一个事件或改变一个主要条件，其他条件保持可比较。读者能看到刚才的对象继续演进，而不是换成另一个预写状态。反馈紧邻主图，直接说明“刚改了什么、哪条规则生效、什么因此改变、什么保持不变”。可以一步步演示、重置、交换事件顺序或比较一个反事实方案，不需要强制猜测、答题或执行命令。

## 图形承担解释

按机制选择表达：集合用保留/移除与来源连线，优先级用明确的选择路径，并发与取消用泳道或时间线，资源所有权用对象与连接。沿真实交互更新图中相同对象，突出本步变化；避免所有题目套“变化前／输入／变化后”三栏。去掉大段旁白后，图形仍应让读者看出核心因果。

把决定本步的短代码或判断放在相应位置，一次只解释当前需要的术语。正文、导航和图中不堆完整路径与内部符号；源码、术语和边界放进后面的参考区。可折叠补充资料，核心结论与理由保持直接可读。视觉服务阅读与比较，不用卡片数量、按钮数量或装饰制造复杂度。

页尾提炼一个可迁移的判定顺序或不变量，并用已经解释的条件变化展示如何继续使用它。新条件不能依赖读者猜测未教过的术语或源码细节。用户希望练习时，可在讲解之后加提取练习与解释性反馈；默认仍是讲解和直接操作，不把答案锁在测验后面。

## 验收分三项

- **事实**：每个判断是否有源码依据？模型省略了什么？假设、反事实和当前实现是否明确区分？
- **运行与呈现**：关键操作是否可用、能重置、键盘可达、离线运行？桌面和手机是否可读？打印是否保留当前图、核心解释与必要参考？
- **教学**：能否用一句具体动词描述学会什么？初次阅读是否只建立一个主模型？能否沿一个实例走到标题承诺的结局？每步能否说清变化及原因？读者能否用提炼的方法解释一种改变后的条件？

主会话亲自走完一条完整路径，再尝试交换顺序或改变条件。语义审读者另查教学项；不得从“事实正确、状态齐全、无溢出、截图未变”推导教学质量通过。不要靠增加题数、字数、状态数、边界说明或截图数解决不好学的问题。
