# C01 一次成功调用如何完成任务

## 本课重点

以新任务标识 `job-1`、处理函数正常返回字符串 `ready` 为场景：调用者传入任务和处理函数，执行函数在当前调用栈中完成一次处理，把结果写回原任务对象后返回。

本课先讲成功路径。有三条结论：任务对象保存数据，执行函数推进状态，处理函数负责具体动作；调用顺序是先记尝试、再处理、最后写完成；返回值与传入任务是同一个对象。失败后能否再调用由下一课展开。

## 主链与职责

```text
调用者：创建 Task(id="job-1")，提供 handle
  → 执行函数：校验上限、确认还有次数
  → 执行函数：status = "running"，attempts += 1
  → 处理函数：接收 "job-1"，同步返回 "ready"
  → 执行函数：result = "ready"，status = "done"
  → 调用者：取得原 Task 对象，读取状态与结果
```

调用者决定处理哪个任务、使用什么业务动作。执行函数不需要知道字符串如何计算，只负责在动作前后维护运行记录。处理函数拿到的是任务标识，没有直接接收整个任务对象；这使接口要求较小，但类型签名没有阻止处理函数通过闭包或其他引用产生外部副作用。

“同步”意味着执行函数直接等待 `handle` 返回，再决定下一步。`queued` 是一个初始状态字符串，不意味着任务已经进入消息队列。没有注册消费者、消息投递或后台调度链路可供追踪。

## 源码阅读

从 [task.py](../../../project/task.py) 的 `Task` 开始，再进入 `run_task`，按本次成功调用的顺序阅读。

### 1. 任务数据的起点

第 6～11 行：

```python
@dataclass
class Task:
    id: str
    status: str = "queued"
    attempts: int = 0
    result: str | None = None
```

`dataclass` 为数据类生成常用方法，包括构造方法。调用者提供标识后，其余字段使用默认值：尚未执行、累计次数为零、没有结果。字段类型便于阅读和静态分析，但没有代码在运行时限制状态只能是这几个字符串，或验证次数非负。这里也没有磁盘或数据库写入；进程结束后不能靠这个对象恢复任务。

### 2. 从入口到处理函数

第 14～21 行的相关部分：

```python
def run_task(task: Task, handle: Callable[[str], str], max_attempts: int = 2) -> Task:
    if max_attempts < 1:
        raise ValueError("max_attempts must be positive")
    while task.attempts < max_attempts:
        task.status = "running"
        task.attempts += 1
        try:
            task.result = handle(task.id)
```

本场景使用默认上限二，零小于二，因此进入循环。执行函数先写运行态，再把尝试次数由零变成一，然后调用处理函数。先增加次数，意味着只要一次处理真正开始，即使随后失败，也已经消耗一次尝试。上限与失败分支的完整关系见 [C02](02-有限重试与异常边界.md)。

`Callable[[str], str]` 描述的是“接收字符串、返回字符串的可调用对象”。它说明双方契约，没有创建线程，也不会校验返回值类型。赋值语句会先计算右侧的调用，调用正常返回后才把返回值存入结果字段。处理函数返回 `ready`，任务结果随之成为 `ready`。

### 3. 成功后结束

第 24～26 行：

```python
        else:
            task.status = "done"
            return task
```

这个 `else` 属于 `try`：只有 `try` 中的处理调用没有抛出异常，才执行完成态和返回。`return` 结束整个函数，即使次数预算还有剩余，也不会为了“用完预算”再调用一次。默认上限二不是必须执行二次。

运行结束时，任务数据为 `id="job-1"`、`status="done"`、`attempts=1`、`result="ready"`。这是代码路径推导的具体值；生成者的成功调用检查也验证了返回对象身份与字段值，不是性能或线上验收结果。

## 机制与边界

### 共享对象让状态直接可见

参数传递的是对象引用，执行函数写的是调用者传入对象的字段，`return task` 没有复制对象。持有同一引用的其他代码会看到更新。因此调用方可以从返回值读取结果，也可以继续使用原引用。

代价是数据更新没有事务回滚。设置运行态和增加次数发生在业务动作之前；若业务动作抛出未捕获异常，之前的更新仍存在，细节见 [C02](02-有限重试与异常边界.md)。同时，这些赋值之间没有锁或版本校验；当前代码只能说明顺序执行行为，不能声称多线程共享同一对象时仍满足某种原子状态转换。

### 状态记录不等于状态约束

初始化、执行前、成功后分别写入 `queued`、`running`、`done`，可以用来解释一次正常路径。程序没有枚举、转换表或状态前置判断；调用者也可以构造其他状态。因此这些字段是运行记录，并非完整状态机约束。

这会直接影响重复调用：入口不会因为任务是完成态而阻止执行，只看次数是否还有预算。这一边界在 [C02](02-有限重试与异常边界.md) 连同失败分支一起解释，不能由本课的成功场景推断出“一个任务只执行一次”。

### 传入处理函数只分离职责

业务逻辑可由不同可调用对象提供，执行函数沿用相同的状态更新流程。这是一种小范围的依赖传入方式，无需把简单教学程序包装成插件架构。它不隔离业务副作用：处理函数若写数据库、发请求，是否安全仍由该业务实现决定。本项目没有这些实现证据。

## 需要懂什么

成功路径成立依赖于明确的时序：处理开始前记入尝试，处理正常返回后才写完成态。这让次数表示已发起的尝试，完成态表示本次调用正常返回；两者表达不同事实。不能把调用开始当作任务完成，也不能把默认状态名当作队列存在的证据。

同步返回交付的是已经在当前调用中取得的结果。若将来改成后台执行，调用者先收到任务标识和最终结果稍后可查询将是另一种契约，需要额外的投递与存储实现；不能仅把函数改名为 worker 就声称异步。

原地修改省去了复制状态和回填的步骤，也把共享可变状态交给了接口使用者。当前程序适合说明单对象、顺序执行的机制；对多处写入或异常恢复的设计，需要另外增加约束。

## 需要记住什么

- 主链：对象初始值 → 上限校验 → 运行态与次数 → 同步处理 → 保存结果 → 完成态 → 返回同一对象。
- 新任务第一次成功时，累计次数是一；预算剩余不会触发额外调用。
- 处理函数只接收标识；执行函数管理状态和计数。类型注解不提供运行隔离或校验。
- 进程内对象、字符串状态、同步调用都不能推出消息队列、持久化或并发安全。面试表达见 [Q1](../任务样本/面经.md#q1-同步执行如何记录状态并交付结果)。
