# C04 重连还能收到哪些事件

> 课程性质：核心<br>
> [返回导学节选](导学.md) · [打开四种游标的交互专题](C04-事件游标.html)<br>
> 对应面试主题：流式回放与会话恢复。掌握层次：理解机制、设计与表达。

## 本课重点

聊天页显示到第三条事件时网络断了，后台仍在执行任务。页面回来后，能补多少取决于两个位置：浏览器最后收到的事件，以及服务器还保留的第一条事件。以 DeerFlow 的内存桥为例，能定位完整 ID 就从下一条继续。若游标序号已落在窗口之前，网关发出缺口通知，让前端从持久状态恢复。

这条链有三个可分别观察的结果：继续收到数据，收到 `gap` 后结束本次订阅，或收到 `end` 表示流结束。只有先分清这三种结果，才能解释为什么用户看到的最后一段文字和后台 run 的状态可能不同。

## 主链与职责

`run_agent 驱动图执行 → bridge.publish(run_id, …) 写事件 → subscribe 按游标选起点 → sse_consumer 编码 SSE → 客户端处理数据、gap 或 end`

worker 负责推进图，流桥按 run 保存有限的回放窗口。网关订阅窗口，把普通数据、心跳、缺口和结束转换成 HTTP 响应中的不同内容。创建执行的连接与后来加入观察的连接可以订阅同一 run，两者断开时的取消策略不同。

## 源码阅读

1. 从 `start_run` 进入后台调用与 `run_agent`。worker 先向桥发布包含 `run_id` 和 `thread_id` 的 metadata，然后消费 `agent.astream`。多模式分支将事件交给 `_publish_stream_item`；若事件来自子图，事件名保留子图命名空间，这样子图的状态快照不会替换整条对话的状态。收尾时调用 `publish_end`。 [运行入口](https://github.com/bytedance/deer-flow/blob/5ecc1c2ac2de624af354bc515d5cb04f80df226c/backend/app/gateway/services.py#L1745) · [worker](https://github.com/bytedance/deer-flow/blob/5ecc1c2ac2de624af354bc515d5cb04f80df226c/backend/packages/harness/deerflow/runtime/runs/worker.py#L891)
2. 看 `MemoryStreamBridge.publish` 如何给事件编号。ID 由毫秒时间戳和这个 run 内从零开始的序号组成。窗口超容量时，桥移除头部并累加 `start_offset`。`_resolve_start_offset` 用「序号减去窗口起点」计算本地索引，然后核对完整 ID。`subscribe` 在读取期间也检查下一个待读位置，处理已连接但消费速度落后的观察者。 [内存事件桥](https://github.com/bytedance/deer-flow/blob/5ecc1c2ac2de624af354bc515d5cb04f80df226c/backend/packages/harness/deerflow/runtime/stream_bridge/memory.py#L75)
3. 到 `sse_consumer` 看网络边界：从请求头读取 `Last-Event-ID`，普通事件带上 ID，流桥的心跳变为 SSE 注释；收到 `StreamGap` 时发送无 ID 的 `gap` 帧并返回，载荷含请求游标、窗口两端和 `reload_durable_state`。正常收尾收到结束标记才发出 `end`。观察接口调用这个消费者时关闭创建端的断线策略。 [SSE 消费者](https://github.com/bytedance/deer-flow/blob/5ecc1c2ac2de624af354bc515d5cb04f80df226c/backend/app/gateway/services.py#L2465) · [创建与观察接口](https://github.com/bytedance/deer-flow/blob/5ecc1c2ac2de624af354bc515d5cb04f80df226c/backend/app/gateway/routers/thread_runs.py#L1347)

## 机制与边界

取同一 run，假设容量为三，当前仅存序号 2、3、4。游标若精确命中 3，客户端下一条收到 4；游标若指向 1，桥会直接给 gap，防止客户端把 2 到 4 当作完整的接续。一个序号为 3、时间戳却不匹配的 ID 走另一个分支，从 2 起回放。省略游标时也从 2 开始，原因是此次订阅没有声明先前的位置。 [切换四种重连条件，看第一条返回什么](C04-事件游标.html)

`gap` 表达的是此次回放存在缺口，run 可以继续执行。加入已有 run 的观察连接关闭，也不会触发创建者的断线取消策略。真正的取消需要满足创建连接确实断开、策略为 `cancel` 且 run 在本 worker 本地仍处于 pending/running 等条件。分开这两件事，才能让“另开页面看进度”保持只读。

Redis 桥沿用缺口这一跨层信号，但具体寻址取决于后端。内存桥对格式错误的游标从保留头部回放；Redis 在已有数据且尾部为普通事件时把此类游标定位到当前尾部，接收后续事件。Redis 用事务一起读取最早 ID、最晚 ID 和非阻塞 `XREAD` 结果，阻塞读取负责唤醒，唤醒后再次检查窗口。这避免先看界限、再读数据期间恰好发生裁剪。 [RedisStreamBridge.subscribe](https://github.com/bytedance/deer-flow/blob/5ecc1c2ac2de624af354bc515d5cb04f80df226c/backend/packages/harness/deerflow/runtime/stream_bridge/redis.py#L241)

## 需要懂什么

一个游标只有在给定 run 的回放窗口中才有意义。窗口裁剪让流桥可以限制缓存占用，也让完整补发有了明确的条件。已淘汰的序号缺少可核对的原 ID，即便是其他来源的数字 ID，内存桥同样保守地报告 gap。客户端此时能恢复的是持久状态呈现的结果；窗口已经丢掉的每一段 token 无法靠再次订阅补齐。

## 需要记住什么

worker 发布，流桥定位，网关传递控制信号。内存桥记三句：完整 ID 命中就读它后面；数字序号低于窗口就报 gap；其他未知 ID 从当前头部读。若要沿源码读到浏览器，接着看前端怎样回读持久状态并重订阅。[recoverStreamReplayGaps](https://github.com/bytedance/deer-flow/blob/5ecc1c2ac2de624af354bc515d5cb04f80df226c/frontend/src/core/api/api-client.ts#L337)
