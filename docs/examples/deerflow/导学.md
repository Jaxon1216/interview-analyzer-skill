# DeerFlow 全栈源码导学 · C04 节选

这份节选沿用原导学的项目地图、课程路线和记忆提纲，聚焦一次断线重连。读完后应能解释三件事：客户端用哪个 ID 找到原运行，事件桥凭什么判断发生缺口，缺口出现后页面如何继续显示当前状态。源码基线为 [DeerFlow `5ecc1c2a`](https://github.com/bytedance/deer-flow/commit/5ecc1c2ac2de624af354bc515d5cb04f80df226c)。

## 项目地图

| 想定位的事 | 状态由谁掌握 | 先看的源码 |
| --- | --- | --- |
| 线程里有一项运行 | Gateway 接受请求，RunManager 管运行记录与线程操作互斥，后台 worker 驱动图 | [start_run](https://github.com/bytedance/deer-flow/blob/5ecc1c2ac2de624af354bc515d5cb04f80df226c/backend/app/gateway/services.py#L1745) · [run_agent](https://github.com/bytedance/deer-flow/blob/5ecc1c2ac2de624af354bc515d5cb04f80df226c/backend/packages/harness/deerflow/runtime/runs/worker.py#L891) |
| 浏览器刚错过了几条事件 | 事件桥拥有有限回放窗口；前端可以读持久状态，按当前 run 重新订阅 | [MemoryStreamBridge](https://github.com/bytedance/deer-flow/blob/5ecc1c2ac2de624af354bc515d5cb04f80df226c/backend/packages/harness/deerflow/runtime/stream_bridge/memory.py#L75) · [recoverStreamReplayGaps](https://github.com/bytedance/deer-flow/blob/5ecc1c2ac2de624af354bc515d5cb04f80df226c/frontend/src/core/api/api-client.ts#L337) |

worker 发布增量 → 事件桥按 run 保留最近事件 → 连接恢复时查游标，遇到缺口回读线程状态 → 浏览器重新订阅，历史列表按线程消息序号整理。

## 学习重点与记忆提纲

先画出三种身份：thread 串起多轮消息，run 标识一次执行，事件 ID 仅定位一次执行中有限窗口内的事件。把“恢复”拆成定位运行、补当前状态、续听新事件三个动作。[阅读 C04 课文](04-事件回放.md)

## 选读

多 worker 部署时可接着读 Redis 事件桥的裁剪、读取与键过期。对比同一个未知游标在两个后端的起点，理解为什么内存桥的规则不可直接套用。[RedisStreamBridge.subscribe](https://github.com/bytedance/deer-flow/blob/5ecc1c2ac2de624af354bc515d5cb04f80df226c/backend/packages/harness/deerflow/runtime/stream_bridge/redis.py#L241)
