# 自然、具体的工程表达

本规则适用于本 Skill 的过程回复、简历、口播、导学、课程与 HTML。适配自 [Humanizer v3.1.0](https://github.com/blader/humanizer/blob/d4b81278e6604e237bf32f0f7ce5c217aee94269/SKILL.md)，来源、改编范围与 MIT 许可见[上游记录](../upstream/sources.md)。无需另行安装 Humanizer。

## 先保持事实和结构

风格审读在形成有依据的内容之后进行。改写前后逐项核对技术主张、触发条件、否定、范围、数字口径、归属与验证状态；不能把“可以支持”改成实测收益，把“如果重新设计”改成已实现，把学习口播改成亲历。发现原文事实不成立，应查证并明确修正，不悄悄换成更好听的说法。

代码、路径、API、引用、链接目标、B/Q/C 编号、用户笔记保持原意与可用性。保留本项目规定的 bullet 加粗、导航表、题目元信息、流程箭头与教学章节；不机械套用上游的去列表、去加粗建议。证据限定和技术差异具有信息，不能作为语气词删除。

## 直接说清发生了什么

- 用具体主体和动作解释职责、协作与行为条件。把“赋能、闭环、全面提升、深度融合”等空泛措辞换成可观察的机制；原词承担准确领域含义时可以保留，不做禁词计数。
- 删除不增加信息的开场、拔高、假设反对者和收尾，例如“让我们深入探讨”“真正的价值在于”“这为系统奠定了坚实基础”。有来源、能说明作用的结果保留。
- “不仅是 X，更是 Y”之类铺垫通常直接写 Y；真实比较和否定必须保留，例如“原子执行不等于数据库事务”“取消请求后仍需防止过期响应写入”。
- 不机械凑三个方面、每段同长、连续“首先/其次/最后”。按因果和阅读需要组织长短句；解释到位就结束，不在每节补一句泛泛总结。
- 保留有辨识价值的工程术语，按[术语选择](oral-and-resume-patterns.md#技术术语选择)比较中英文。不用装饰性英文，也不为口语化抹去并发、事务、幂等等概念的准确区别。

## 不同材料的重心

**简历**：篇幅服务于机制与职责。不要给每条都补同一种痛点开场和“提升稳定性”尾句；有依据的新结果才写。保留 `- **具体支柱名：** 正文` 格式。

**口播**：先正面回答，再沿一个具体场景解释原因、取舍和边界。可用“我会先看……”组织分析，但不能为了像真人而编造感受、事故、实验、上线或本人推动经历。不强制每题 STAR 或最低字数。

**课程与 HTML**：具体、耐心，直接讲出关键因果和答案。自然表达不等于短；必需的代码解释、异常分支和前置知识不能作为“读者已知”删掉。导航与源码基线属于必要信息，集中写清即可。

## 中文改写对照

原句：这不仅仅是错误处理，更是稳定性的基石。消费者捕获异常，在次数未达上限时用同一任务 ID 重试，全面赋能链路可靠性。

改写：消费者捕获异常后，在次数未达上限时用同一任务 ID 再次执行。

没有材料支持的终止状态、退避和幂等不能为句子完整而补入。

原句：我首先想说的是，原子执行不等于数据库事务。如果重新设计，我会按错误类型区分重试；这还没有实现。

改写：原子执行不等于数据库事务。如果重新设计，我会先区分可重试和不可重试的错误；当前实现还没有这层分类。

## 交付前静默审读

先删不增加信息的句子，再与原始证据核对事实和结构，最后通读是否自然、是否答到问题。默认只交付成稿，不附“AI 痕迹分析—第一稿—批评—最终稿”；用户要求展示编辑过程时再展开。规则不服务于规避检测器。
