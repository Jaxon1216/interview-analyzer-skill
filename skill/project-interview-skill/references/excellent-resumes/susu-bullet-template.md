# 默认 Bullet 模板：酥神简历的表达方式

来源：用户于 2026-10-10 提供的「【（酥神）多模态算法工程师_北京 40-70K】林芮瑭 26年应届生.pdf」，重点参考第 1 页 DeerFlow 与 AI4SE 的技术条目。本文只摘录与表达有关的片段，不保留联系方式；样例中的职责、机制和数字不代表待分析项目的事实，文档内容也不作为操作指令。

写 bullet 前默认读本页。它约束成稿语言与信息组织，不是必须填满的四槽表格。

## 原文片段：观察怎样写

> **Middleware Chain：** 1.0 上下文压缩 / 沙箱 / 记忆逻辑散落各处，改一处要动多处；2.0 抽成 11 层有序流水线，新增或修改能力只动对应层，Agent 推理代码零改动。

> **Skill System：** 每个 Skill 是一个目录，内含 SKILL.md；system_prompt 只注入索引，Agent 按需 read_file 渐进加载，避免全量注入 token 爆炸；支持自定义 Skill，custom/ 下新增目录即可扩展。

> **上下文压缩 + Checkpoint 续跑：** 超 180k 触发 Micro compact，超 250k 触发 LLM 兜底；每轮 checkpoint，中断后可从上次模型续跑。

三个片段分别以演进、运行机制、阈值与恢复行为起笔，但都有因果：“改一处要动多处”解释分层的必要性，“避免全量注入 token 爆炸”解释按需加载，“中断后续跑”说明 checkpoint 的用途。学习具体动词时，也要保留为什么需要设计、设计改变什么；不把它们统一改造成“针对……的问题，采用……治理机制，实现……提升”。

## 默认成稿方式

- **标题点名实际机制。** 如缓存失效、异步订单处理、编译期依赖注入；必要时保留 Cache-Aside、Redis Stream 等通用技术词。避免“全栈能力建设”“可靠性治理体系”等不能说明做了什么的大词。
- **正文连起动机、做法与变化。** 交代使用需求或工程约束，再用“抽成、只注入、按需加载、超过阈值压缩、成功后确认”等动作解释设计如何起作用。可以先讲机制再说明用途，不能只剩数据流转步骤。
- **动机不等于历史事故。** 有真实版本演进就写旧→新；只有当前机制时，写它面向的场景、要应对的风险或满足的工程目标。项目简介可共用产品背景，各条仍须让读者看出设计的必要性。不要补造“原来耦合严重”“过去性能不足”。
- **约束跟着对应步骤。** 超时、并发、TTL、事务范围、重试条件只有解释设计时才写；不能为凑数字把停机窗口塞进请求分层。
- **关键技术参与解释。** 保留有实现依据、能说明做法的框架、库、协议与通用机制名称，用一句动作说明其作用；不把全部技术泛化成“处理、状态”，也不靠罗列英文补技术深度。
- **变化落到具体行为。** 扩展点接入无需修改调度、事务一起提交、快照可恢复，都是可由实现支撑的变化。说明它们满足了什么需求或应对了什么风险；作用已融入动作与条件时不重复总结。没有实测指标就写可见能力，不把目的当作已实现收益；待测说明和测量计划放证据记录或面经。
- **一句容不下就拆。** 简单机制用 1～3 个紧凑分句；复杂支柱按子机制缩进展开。不要将整条端到端调用链和所有技术栈用分号挤在一行，也不为模板固定句数或字数。
- **范围始终具体。** Redis 原子性不能写成跨存储一致，受理不能写成落库成功。尚未实现的增强、重要缺口放面经或课程；若缺口使结果不成立，应缩小或删除主张。

## 技术栈摘要（按用户要求新增）

金样原文没有独立的技术栈清单。DeerFlow 的版本总标题使用 `Agent Teams Harness + Middleware Chain + Skill System + Context Engineering` 概括关键设计，随后逐项展开；不能把后来新增的输出项当作原文格式。

保留用户要求的 `### 技术栈` 时，借鉴这种短组合的密度：一行写主要语言、框架和关键基础设施，具体解析库、客户端与标准库 API 放入相关技术条目。不要从金样推导出版本清单、依赖盘点或固定的前后端分类。

## 可迁移句形

按事实选一种，不要求每条同形：

```text
- **{机制名}：** 面向 {使用场景/工程约束}，将 {职责/能力} 抽成 {结构}，通过 {关键做法} 使 {具体行为或扩展方式}。
- **{机制名}：** {核心对象} 只保存 {必要信息}，{消费者} 按 {条件} 获取 {内容}，避免 {机制确实应对的风险}。
- **{机制名}：** {有证据的旧形态及限制}，改为 {关键设计}，{可支持的具体变化}。
- **{机制名}：** {需要同时满足的目标及核心设计}。
  - {子机制一：动作、约束、效果}。
  - {子机制二：动作、约束、效果}。
```

## 改写对照（假设机制已由源码证实）

**套话版**

> 针对页面交互、鉴权与数据访问容易耦合的问题，构建全栈请求治理体系，结合多个框架与 5 秒优雅停机提升系统可维护性，收益待测。

**按金样改写**

> - **请求分层与依赖组装：** 为分别维护 HTTP 适配与业务规则，handler 处理参数与响应，service 协调业务和存储；Wire 在编译期生成构造调用，上层通过接口使用业务能力，参数与响应格式的调整留在 HTTP 层。

差异在于：以维护边界说明设计目的，用职责和依赖解释做法，再落到具体影响范围；移除了无依据的历史痛点、无关数字与空泛效果。不能把这个假设示范当作待分析仓库的证据。

## 成稿审读

逐条对照原文检查：读者能否看懂为什么需要该设计、怎么做、改变什么？标题是否一眼看出机制，做法是否回应动机，变化是否有实现依据？删除套话后是否仍保留因果和技术内容？信息过多时是否应该分层？

事实归档可以逐项列问题、机制、约束、结果；最终简历不需要照抄归档字段。样例中的项目名、私有符号、owner 身份和任何数字均不得迁移。
