## 本课重点

以新任务第一次处理抛出 `ValueError`、第二次返回 `recovered` 为场景。当前实现会把第一次尝试标成失败，再在下一轮改回运行态，第二次成功后返回完成任务，累计次数为二。失败状态不会直接结束函数；剩余次数才决定能否继续。

本课讲清四条结论：上限包括首次执行；累计次数保存在任务对象中，不会在每次入口重置；只有处理调用中的 `ValueError` 被捕获；次数限制不等于幂等、退避或超时。

## 主链与职责

```text
校验 max_attempts >= 1
  → attempts < max_attempts？
    否：直接返回原任务，字段不再变化
    是：写 running，次数加一，调用处理函数
      正常返回：写结果 → done → 立即返回
      ValueError：failed → 回到循环条件
      其他异常：向调用者传播，函数不正常返回
```

执行函数负责重试决策，处理函数负责抛出什么异常。调用者提供总上限，并决定如何接收正常返回的失败任务或向外传播的异常。没有单独重试队列，下一次尝试就在当前同步调用中立即发生。

## 源码阅读

本课仍读取 [task.py](../../../project/task.py)，按“入口校验 → 次数门槛 → 一次尝试 → 出口”的顺序定位 `run_task`。

### 1. 入口校验不是业务重试

第 15～16 行：

```python
if max_attempts < 1:
    raise ValueError("max_attempts must be positive")
```

这个错误发生在 `try` 之前，不会被下方的 `except ValueError` 捕获。上限零会直接抛出参数错误，处理函数一次也不调用，任务字段也尚未改变。相同异常类并不代表走相同恢复路径，还要看异常在什么范围内产生。

当前只检查上限是否小于一，没有检查参数必须为整数，也没有验证已有次数的类型或是否非负。类型注解表达意图，不提供这些运行时校验。讨论预算时，下面按正常的整数上限和非负整数累计次数解释。

### 2. 总预算包含首次尝试

第 17～19 行：

```python
while task.attempts < max_attempts:
    task.status = "running"
    task.attempts += 1
```

新任务次数零、上限二，允许第一次和第二次处理调用；不是“首次执行加两次重试”。已有一次尝试的任务，在相同上限下只剩一次。已有次数等于或超过上限时，循环不会进入，末尾直接返回原对象，甚至不会把状态改成失败。

计数在调用前增加，记录发起了多少次尝试，而非成功了多少次。正常整数条件下，本次最多新增 `max(0, max_attempts - 原有 attempts)` 次处理调用；一次成功则提前停止。

### 3. 指定异常回到循环，成功直接返回

第 20～27 行：

```python
try:
    task.result = handle(task.id)
except ValueError:
    task.status = "failed"
else:
    task.status = "done"
    return task
return task
```

失败分支没有 `return`，所以会继续判断 `while` 条件。`try` 的 `else` 仅在调用正常返回时执行，它把状态改成完成，并结束整个函数。末尾的 `return` 则承接循环耗尽或一开始就无预算的情况。

第一次抛出 `ValueError` 时，调用右侧没有产生返回值，因此结果赋值没有完成，任务被标成失败。下一轮开始后状态被重新写成运行中。第二次正常返回后，保存 `recovered`，写完成态并返回。若两次都抛出指定异常，最终状态为失败，次数为二，初始没有结果则仍为 `None`。

## 机制与边界

### 三种出口给调用者不同契约

| 条件 | 处理调用次数的变化 | 对调用者的结果 | 对象字段 |
| --- | --- | --- | --- |
| 某次正常返回 | 本次已加一，随后停止 | 正常返回原对象 | 完成态，结果为本次返回值 |
| `ValueError` 持续到耗尽 | 每次尝试加一 | 正常返回原对象 | 失败态；已有结果不会被清空 |
| 处理函数抛出其他异常 | 抛出前已加一 | 异常向外传播 | 保留运行态和已增加的次数 |
| 进入时已经无预算 | 不增加 | 正常返回原对象 | 原有状态和结果保持不变 |

返回一个任务对象不能单独证明处理成功，调用者必须结合状态与本次是否进入执行来解释。处理函数抛出 `RuntimeError` 时，写完成或失败的分支都不会运行，所以留下运行态；这只是一次异常中断后的残留，不能解释成后台仍在执行。

如果对象原来带着旧结果，而本次处理失败，赋值不会完成、异常分支又没有清空结果，就会同时出现失败态和旧结果。因而结果非空也不能单独当作本次成功的依据。当前缺少错误原因字段，失败态无法直接告诉调用者是哪次错误或错误内容。

### 累计预算与终态是两套规则

循环只看次数，不看任务状态。新任务第一次成功后，次数为一；再次用默认上限二调用，同一任务还会处理一次，并可能覆盖先前结果。若次数已经为二，即使状态仍是初始态，也会直接返回。`done` 与 `failed` 并不是入口强制执行的终态。

当前状态字段可以帮助讲述执行过程，却不能提供严格的合法状态转换或完成任务去重。若要演进，可以先明确“完成后复用结果”“失败是否允许续跑”的业务规则，再实现入口判断。需要保留次数累计还是为新一轮执行创建独立记录，也取决于想表达“同一个任务”还是“同一次执行”。这些都尚未实现。

### 重试资格由异常类型粗略决定

源码把处理调用中的 `ValueError` 统一当成可继续尝试的失败，并没有检查错误是否暂时、输入是否可修复。对于确定性输入错误，相同任务标识再次调用可能仍然失败。若重新设计，需要由业务语义区分可重试错误和不可重试错误，而不能把 Python 异常类当作通用的暂时故障标准。

该分支还会捕获 `ValueError` 的子类；它不会捕获其他无继承关系的异常。即便扩大捕获范围，也不能据此得出错误已经安全恢复：还需要定义终态、保留原因并决定哪些错误应向外传播。

### 有限次数不能消除重复副作用或等待

每次重试都传入相同任务标识。若处理函数先写入成功、随后抛出指定异常，下一次调用可能重复写入。相同标识只提供可用于幂等设计的输入，当前没有唯一约束、已处理记录或事务，不具备幂等保证。

循环也没有等待间隔，失败后会立即开始下一次；没有总期限或单次超时。如果处理函数一直不返回，循环无法走到下一次预算检查，有限次数不能限制这次调用的等待时间。退避、超时、取消、幂等与持久化是不同问题，需要在真实需求出现后分别设计，不能用“有限重试”概括为全部已解决。

## 需要懂什么

重试控制由“尝试前记数、失败后不返回、循环前检查预算”三部分共同产生。只看到 `except` 中写失败态，还不能判断函数就结束；要继续看控制流下一跳。成功分支的立即返回则说明预算是上限，不是执行次数目标。

次数属于任务对象，意味着重新进入执行函数会接续旧计数。它没有按每次函数调用重置，也没有按完成态停止。状态、预算与准入是三项独立规则，当前只实现了字段记录和次数门槛。

异常边界由捕获范围和类型共同决定。参数校验虽然抛出同名异常，却发生在捕获范围外；非指定异常虽然来自处理函数，却不满足捕获类型。异常传播不会撤销先前的原地更新。

当前实现能说明顺序执行中的有界调用行为，无法证明业务操作可以安全重复，也无法保证进程中断后继续。分析到这些边界即可支撑本项目的后端表达，无需补造消息系统或生产事故。

## 需要记住什么

- 默认上限二含首次调用；次数先增加，成功后立即停止。
- 指定异常：失败态 → 若有预算则再次运行；耗尽后正常返回失败对象。
- 非指定异常向外传播，可能留下运行态；无预算直接返回原状态。
- 完成态不会阻止重入，失败也不会清空旧结果。状态与结果都需要结合执行上下文解释。
- 有限重试没有提供幂等、退避、超时或重启恢复。相关表达见 [Q2](../任务样本/面经.md#q2-有限重试如何决定继续与停止)，状态归属见 [Q1](../任务样本/面经.md#q1-同步执行如何记录状态并交付结果)。
