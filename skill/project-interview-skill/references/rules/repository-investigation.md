# 仓库探索与证据归档

写导学和面经前执行。目标是找出**能由用户职责和项目证据共同支撑**的工程支柱，不是罗列目录、技术栈或测试文件。用户只提供描述而没有仓库时，明确标注「仅据描述」；不得假装看过源码。

## 1. 确定分析边界

- 确认目标项目根目录、主要语言和可运行入口；区分业务源码、生成代码、依赖、示例与测试。
- 从 README、架构说明、配置和入口文件了解产品目标，再对照用户描述确认候选人的实际职责。仓库存在某机制，不代表候选人实现过它。
- 仓库很大时，按用户职责和主要链路选代表性模块，不要求逐文件扫完。仓库很小或材料不足时，保留实际找到的数量，不为凑亮点扩写。

## 2. 沿链路追踪，而非按目录摘抄

对 2～4 条最能解释项目价值的核心链路，追踪「入口 → 状态/数据变化 → 关键机制 → 对外结果」。每条至少找出：

1. **为何存在**：旧方案、失败模式、需求或约束是什么？没有历史证据就写当前要解决的问题，不编造旧架构。
2. **如何工作**：调用关系、状态转换、数据契约，以及跨模块的责任分界。
3. **哪里会失败**：超时、并发、一致性、重试、降级、回滚、资源预算、权限或观测；按项目实际选，不机械套全项。
4. **如何证明**：实现、测试、配置、文档、运行结果分别能证明什么；结果是代码可见的架构效果，还是需要测量的线上收益。

对每条候选支柱记录一行事实卡：`问题/演进 | 我的动作与职责证据 | 机制 | 硬约束/边界 | 结果 | 源码/测试/文档相对路径 | 可信度与缺口`。路径指向关键实现或测试，能标行号时标行号。事实卡可先放在工作草稿；成稿将有价值的证据写进导学的「链路与证据」及面经的「源码证据索引」。

## 3. 筛选含金量

优先选择能回答「为什么这样设计、与什么方案相比、失败时怎样、怎样验证」的事实；跨模块约束、架构演进和系统机制优先于单点功能。每个一级简历 bullet 应有一条可回查的事实卡；没有职责证据时，用「项目采用」解释项目，不写成「我主导」。没有可验证结果时，说明待验证的指标与测法，不用空泛收益充数。

发现关键事实缺口时，先完成能独立进行的仓库探索，再向用户集中询问所有权、上线效果或旧方案等高信号问题。无法确认的事实保留为待确认，不进入肯定口吻的简历 bullet。
