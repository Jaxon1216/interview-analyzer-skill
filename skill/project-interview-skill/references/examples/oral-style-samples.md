# 口播与自然追问样例

以下仅示范表达与对话关联，不代表用户项目已实现这些机制。生成时替换成真实源码，不复制场景、职责或指标。默认调性为通用工程语言＋少量解释过的内部符号。

## 前端：服务端渲染与失败降级

**目标 bullet**：面向首页首屏与可用性需求，采用 Streaming SSR 输出首屏内容，对预取数据做契约校验，并在服务端渲染失败时回退客户端加载；客户端依据渲染状态选择水合或补发请求。

**主问**：为什么首页采用服务端渲染，又为什么保留客户端回退？

**触发依据**：bullet 中“Streaming SSR”和“失败时回退客户端加载”。

**口播版**：

我关注两个目标：让首屏尽早展示内容，同时避免服务端某一环节失败就让页面不可用。服务端先预取并校验数据，再输出可以接管的 HTML；客户端拿到与服务端一致的初始数据后进行水合。如果预取或渲染失败，客户端根据明确的状态重新加载并走 CSR。这让首屏路径和可用性兜底都有出口。取舍是两端必须统一数据契约、首屏输入和错误状态，否则回退可能重复请求，水合也可能出现不一致。效果应分别观察首屏指标、水合错误和回退比例，不能仅凭使用 SSR 就判断性能收益。

**追问**：你说两端要使用一致的初始数据，哪些情况会破坏一致性？

**触发依据**：主回答中的“两端必须统一……首屏输入”。

**口播版**：

常见原因是首次渲染的时间、随机值、身份或环境输入不同。例如服务端按游客渲染，客户端却立即按本地登录态输出另一套 DOM。我会先固定并序列化首屏输入，让客户端首次渲染沿用它，再在接管后更新身份或浏览器专属信息。只在浏览器可用的 API 放在客户端生命周期中。这样能把“首次输出一致”和“接管后允许变化”分开；具体仍需结合框架的水合规则验证。

## 后端：异步下单与失败恢复

**目标 bullet**：面向集中抢购，采用 Redis Lua 原子执行资格判断、库存预扣与消息入队，通过消息消费者异步落库，并用数据库约束与事务控制重复写入和库存更新边界。

**主问**：为什么库存预扣和入队放在同一个 Lua 脚本里？

**触发依据**：bullet 中“原子执行资格判断、库存预扣与消息入队”。

**口播版**：

如果拆成多个请求，资格判断后可能被并发修改，预扣成功与入队之间也会留下间隙。我把这些 Redis 内的操作收进同一段脚本，减少客户端往返和命令间交错，让消费者后续处理数据库写入。这里的边界必须讲清：脚本原子执行不等于数据库事务，也不表示命令运行错误会自动回滚之前的写入；因此要预先校验键类型和输入，并处理异常状态。异步返回也只表示请求被接受，最终订单成功要看落库状态，不能拿返回订单号替代成功确认。

**追问**：既然脚本不能保证数据库提交，消费者失败后怎么办？

**触发依据**：主回答中的“最终订单成功要看落库状态”。

**口播版**：

我会先看现有消费模型是否保留未确认消息，以及落库是否可幂等重放。落库成功后才确认消息，失败记录原因并有限重试；业务唯一约束负责拒绝重复订单，事务负责把相关数据库更新绑定在一起。永久失败还需要补偿或对账，让预扣库存与实际订单重新收敛。如果源码只有重试而没有补偿，这部分就作为演进方案讲清，不能因为用了消息队列就认定一致性已经解决。

## 反例与修正

- 私名堆叠：“进入某 hook，再调用某内部 action，设置某枚举与开关。”改为状态所有者、转换条件与错误边界；具体路径与符号进入证据索引。
- 提前知道源码：“你那个预热函数为什么把两个字段写反？”只有简历或前序回答明确提到此事故才能这样问；否则改为“如何验证地理索引和距离排序正确”。
- 突然跳题：列表聚合回答后直接问 Feed 游标。应先介绍 Feed，或设独立支柱，见[问题契约](../rules/star-framework.md)。
- 用未测指标撑结果：“上线超卖率为零、P95 200ms。”只有真实测量才能这样写；没有数字时讲实现的正确性边界与具体验证方法。
- 错误降级：“Redis 故障就用本地库存保证全局不超卖。”本地状态无法替代多实例的全局约束，需结合实际库存事实源与服务策略设计，不能复制成通用兜底。
