# 口播叙述与简历（抽象模板）

本文件是**可移植规则**，适用于任意项目 / 岗位。写简历 bullet 前默认打开[酥神 bullet 模板](../excellent-resumes/susu-bullet-template.md)，按需再读 [excellent-resumes/](../excellent-resumes/README.md) 的项目级金样；**不要**把金样里的产品名、层名、数字抄进用户项目。生成 bullet 时同时对照领域中立的 [bullet few-shot](../examples/bullet-few-shots.md)，只学习结构，不复制素材。

成稿同时遵从[自然表达规则](writing-style.md)：删无信息铺垫与总结，保留条件、术语、证据边界与本文件规定的结构；不为增加口语感编造个人经历。

## 回答组织

回答先回应问题，再解释机制、项目例子和边界。项目方案题可用 STAR；原理、故障、演进题按[问题契约](star-framework.md)选择结构，不统一设最低字数或强制重讲背景。

目标模式的项目示范用第一人称，供学习掌握后使用；概念解释可直接说技术。文首说明一次目标定位，不把职责或测量免责声明重复塞进每题。内部私名少量使用并解释，具体定位下沉到源码索引。

---

## 简历「项目简介 / 一句话」写法

用 **1～2 句** 说清：**做什么 + 关键技术/形态 + 可选一句价值**，避免形容词堆砌。

**抽象公式**：

> 基于 {核心技术栈/范式} 的 {产品形态}，用户/业务侧能 {核心操作}，系统支持 {关键能力 A、B}，{可选：差异点如同步/异步、端侧等}。

**示例形态（勿照抄项目名）**：

> 基于 AI 大模型的智能 BI：用户上传 Excel 后，AI 自动生成 ECharts 图表与分析结论，支持同步/异步生成与拖拽看板组合多图。

面经文档中的 **项目概要** 必须接近此密度与信息量，可直接贴简历「项目描述」栏。有真实 star / 奖项可以写；没有就省略，禁止编造。

## 先定简历海拔（写 bullet 的第一步）

先看完整分析范围：项目替用户完成什么，哪些组件负责决策、执行和状态，哪些机制支撑核心能力。查证这些职责如何协作后，再按系统重要性、目标相关性和设计辨识度组织支柱；不能把输入材料的分组直接改成同数目的条目。架构与系统机制优先，真实演进仅在能解释设计时使用，不因存在旧版本就优先于核心机制；缺少业务材料时按已知工程目标组织。

| 海拔 | 形态（按形态识别，不锁项目） | 默认去向 |
|------|------------------------------|----------|
| 架构演进 | 旧形态 → 新形态：固定流程变为可编排；逻辑散落变为可扩展分层 | 一级支柱 |
| 系统机制 | 状态/一致性、隔离、预算、降级、扩展点、契约 | 一级，或该支柱的二级 |
| 交互 / 实现细节 | 某一控件、协议字段、文件读写或权限检查 | 归入所服务的机制；有设计辨识价值的留在正文或二级，其余进入追问 |

- **求职方向只调口播侧重点，不改变简历海拔。** 不要把系统机制降成该方向上的功能清单（前端写成页面交互列表、后端写成 CRUD 列表、AI 写成调了某个模型）。优先写值得掌握的架构支柱，再按方向讲清链路上的落点。
- 贡献模式且用户明确只做子模块时：一级 bullet 仍写**该模块**的机制与约束；不要把局部改动扩成全仓 owner，也不要把全仓边角堆成多条工单。
- **禁止**把导学「重点亮点与学习顺序」原样粘成简历 bullet。导学是读代码地图，简历是面试官 30 秒能追问的支柱。

目标模式按仓库机制写有力度的目标表达，不因缺少作者证据退成修复清单；不主动审计作者。用户明确参与的内容在含金量相近时优先。

用户要求只整理实际贡献时，按其说明选择职责动词；局部参与写清模块边界，不需要扩大到全仓。默认目标模式与贡献模式不要混用规则。

## 简历 bullet 成稿方式

一级通常 4～6 条，数量服从项目实际机制；每条以 `- **具体支柱名：** 正文` 独立成行。标题应让目标领域同行识别设计，采用准确的机制或架构概念，而非把局部动作接上“管理、处理”当作概念。按下文[技术术语选择](#技术术语选择)决定中英文，标题的设计必须在正文中展开。

默认对照[酥神模板](../excellent-resumes/susu-bullet-template.md)的原文语言：直接写动作与运行方式，关键约束放在对应步骤，效果紧随机制；有真实演进才交代旧→新。背景可在项目层共用，不要求每条都以“针对……的问题”起笔。

正文以职责和协作为骨架：谁持有什么状态、向谁传递什么、正常与异常条件如何改变执行或数据流。保留解释这些行为的关键实现细节，不罗列全部节点。问题、机制、约束、结果仅用于查漏；作用可以由条件分支直接体现，不必另补收益句。删掉复述前文的条件与总结，没有可支持的新效果就结束。没有旧架构证据就讲当前机制；指标缺口和测量计划另放证据记录或相关回答。

简单机制用紧凑分句；复杂支柱可以有 2～4 条二级说明，按子机制分层，不挤成包含全部调用节点与技术栈的长句。约束必须相关，不为补数字混入停机、部署等另一主题。

## Few-shot 对齐与审读

1. **支柱抽取**：先识别核心职责和系统机制，再分组；检查整组能否解释项目如何完成主要任务，是否漏掉核心机制、却将附属接口或校验独立成条。支柱名和数量不从金样套取。
2. **事实归档**：按[仓库探索](repository-investigation.md)记录目标、已实现机制、边界、具体效果与证据，核对指标口径和归属；历史演进有依据才写，未实现方案另列。目标模式不以个人职责证据筛选。
3. **语言对齐**：读默认金样原文与[领域中立 few-shot](../examples/bullet-few-shots.md)，学习具体动词、因果和分层方式，不迁移项目素材；按目标岗位判断术语熟悉度，比较中英文后选择自然称呼。
4. **成稿**：围绕支柱说明职责、协作与行为条件；需要展开的重要机制用二级，背景按需交代。具体作用由机制推出，不强行补收益句。
5. **成稿审读**：先看整组选材是否抓住核心，再看每条是否让同行读懂具体设计并自然追问。逐句检查新增信息：是否只有源码动作清单、重复条件或抽象总结？删去尾句后信息未减少就删去；只剩架构大词时补回关键实现。
6. **术语审读**：另行判断名称准确性、同行熟悉度与中英表达优势。术语合格不能证明选材、机制解释或成稿质量合格。

“提升性能、提高稳定性、优化体验、增强可维护性、降低成本”不能单独充当结果。改成有因果的具体变化或真实指标；无法支持的收益直接删除，测量计划不进入简历正文。私有函数、文件路径与内部枚举进入源码证据索引，解释机制所需的常见协议、框架和公开 API 名按下文选择。

## 技术术语选择

本节用于 bullet 标题与正文。以目标岗位、相关技术领域的面试官和同行为读者；方向未指定时按项目实际技术领域判断，不把所有领域术语视为人人熟悉。

1. **事实匹配**：先确认对应机制已实现或有材料支持，再选名称。中英文名称及译名都要核对，不能引入材料未确认的执行载体、并发模型或保证范围，也不能为了使用 RAG、Agent、Context Engineering 等词扩大项目能力。
2. **同行熟悉**：判断是否是该领域常用的概念、协议、框架、缩写或公开 API。公开仓库、搜索结果和某篇文档中出现过，仅说明可找到，不证明同行普遍使用；私有类名与自造英文不因此成为通用术语。
3. **中英比较**：采用更常见、更明确、阅读更自然的一种。英文能提高设计辨识度或表达精度时保留，中文更自然时用中文；存在中文译法本身不是删除英文的理由。不固定加括号翻译。SSR、SSE 等缩写可保留，幂等、限流、事务等中文无需强行改成英文。这些是判断示例，不是固定白名单。
4. **标题与正文分别选词**：标题概括核心机制或架构概念，正文中的术语要解释动作、结构或约束。公开 API 或文件格式名在有帮助时可保留，不把普通中文句子中的所有动作换成英文，也不拿私有组件名作架构标题。
5. **整句审读**：删去不参与机制解释的装饰性名词和技术栈清单；保留必要的技术信息，不能把所有术语都泛化成“处理、约束、状态”。不设英文数量、比例或每条至少一个英文的要求，零英文同样可以合格。

熟悉度不确定时，参考官方文档与相关技术资料核对概念和常用叫法；仍无法确认时用清晰中文，不声称测得行业使用比例。术语取舍留在生成者分析或评测记录，不附在简历正文；用户未要求时不额外交付逐词解释表。

## 反例（禁止的简历调性）

写成下面这样就是**功能工单型**，即使每句都真实也不通过：

> - 接入某某列表刷新：处理两类竞态，成功率（待测）。
> - 开发某某确认弹窗：未知版本降级为纯文本。
> - 把渲染做成节流 / 截断，卡顿（待测）。
> - 接入某某开关与权限门控。

失败特征（按形态识别）：没有解释机制；海拔停在交互细节；结果用（待测）顶上；面试官无法从 bullet 问出「为什么是这种结构、约束怎么来的」。这些内容可以出现在对应支柱的**追问口播**里，不能当一级简历。

项目级失败对照（同一仓库被写成工单清单）见 [excellent-resumes/](../excellent-resumes/README.md) 各金样文末，不要把那里的专有名词带回本文件当规则。

## 名词分层

| 位置 | 允许 | 禁止 |
|------|------|------|
| 简历简介 + 一级/二级 bullet | 与事实匹配、同行熟悉且有解释作用的技术概念、协议、框架与公开 API；bullet 中英文按上节比较 | 仓库私有类/辅助函数名、文件路径、issue 号、私有枚举、打点事件名、灰度开关键 |
| 口播正文 | 通用工程语言为主；黑名单私名每题有次数预算，且必须翻译 | 私名堆叠型（见 `oral-style-samples.md`） |
| 源码证据索引 | 函数名、路径、内部符号 | （此处集中存放即可） |

区分公共技术名称与项目实现标识，不能仅按英文形式、大小写或能否搜到分类。公开 API 有助于解释机制时可留，仓库私有辅助函数下沉到索引；口播的组织方式与私名预算仍按[内部名词规则](internal-terms.md)执行。

## 出题契约

以[问题与回答契约](star-framework.md)为准：先写目标简介与 bullet，再抽取可见主张和触发词，只根据简历拟主问；追问根据简历和前序回答递进，答案由课程和源码支撑。

每个主问记录对应 B、触发依据、考查目标和 C 课程链接。检查题目能否由简历自然引出、答案是否正面回答、追问是否提前使用未知事实；不要靠补标签掩盖脱节。
