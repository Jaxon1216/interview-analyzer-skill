# 口播叙述与简历（抽象模板）

本文件是**可移植规则**，适用于任意项目 / 岗位。写简历 bullet 前再打开 [excellent-resumes/](../excellent-resumes/README.md)，那里才放项目级金样；**不要**把金样里的产品名、层名、数字抄进用户项目。生成 bullet 时同时对照领域中立的 [bullet few-shot](../examples/bullet-few-shots.md)，只学习结构，不复制素材。

## 回答组织

回答先回应问题，再解释机制、项目例子和边界。项目方案题可用 STAR；原理、故障、演进题按[问题契约](star-framework.md)选择结构，不统一设最低字数或强制重讲背景。

目标模式的项目示范用第一人称，供学习掌握后使用；概念解释可直接说技术。文首说明一次目标定位，不把职责或测量免责声明重复塞进每题。内部私名少量使用并解释，具体定位下沉到源码索引。

## 简历「项目简介 / 一句话」写法

用 **1～2 句** 说清：**做什么 + 关键技术/形态 + 可选一句价值**，避免形容词堆砌。

**抽象公式**：

> 基于 {核心技术栈/范式} 的 {产品形态}，用户/业务侧能 {核心操作}，系统支持 {关键能力 A、B}，{可选：差异点如同步/异步、端侧等}。

**示例形态（勿照抄项目名）**：

> 基于 AI 大模型的智能 BI：用户上传 Excel 后，AI 自动生成 ECharts 图表与分析结论，支持同步/异步生成与拖拽看板组合多图。

面经文档中的 **项目概要** 必须接近此密度与信息量，可直接贴简历「项目描述」栏。有真实 star / 奖项可以写；没有就省略，禁止编造。

## 先定简历海拔（写 bullet 的第一步）

优先级：**架构演进 > 系统机制 > 交互 / 实现细节**。

| 海拔 | 形态（按形态识别，不锁项目） | 默认去向 |
|------|------------------------------|----------|
| 架构演进 | 旧形态 → 新形态：固定流程变为可编排；逻辑散落变为可扩展分层 | 一级支柱 |
| 系统机制 | 状态/一致性、隔离、预算、降级、扩展点、契约 | 一级，或该支柱的二级 |
| 交互 / 实现细节 | 某一控件、某一协议字段、某一文件的读写、某一布局约束 | **追问**，不进一级 bullet |

- **求职方向只调口播侧重点，不改变简历海拔。** 不要把系统机制降成该方向上的功能清单（前端写成页面交互列表、后端写成 CRUD 列表、AI 写成调了某个模型）。优先写值得掌握的架构支柱，再按方向讲清链路上的落点。
- 贡献模式且用户明确只做子模块时：一级 bullet 仍写**该模块**的机制与约束；不要把局部改动扩成全仓 owner，也不要把全仓边角堆成多条工单。
- **禁止**把导学「重点亮点与学习顺序」原样粘成简历 bullet。导学是读代码地图，简历是面试官 30 秒能追问的支柱。

目标模式按仓库机制写有力度的目标表达，不因缺少作者证据退成修复清单；不主动审计作者。用户明确参与的内容在含金量相近时优先。

用户要求只整理实际贡献时，按其说明选择职责动词；局部参与写清模块边界，不需要扩大到全仓。默认目标模式与贡献模式不要混用规则。

## 简历 bullet 四槽公式（正例配方）

一级通常 4～6 条，证据不足时宁可少写。每条以 `- **具体支柱名：** 正文` 独立成行，先给可概括该机制的标题，再展开四槽（可写在同一句，也可用 2～4 条二级展开）：

1. **痛点或演进**：以前为什么不行（散落、不可扩展、无预算、失败不可见）。
2. **机制**：业界可检索的结构名 + 一句话怎么做。
3. **硬约束或数字**：层数、并发、超时、配额、SLO、接口个数。这是设计约束，不是装饰。
4. **结果**：架构效果（主路径零改、可降级、可续跑）或真实指标。没有数就写架构结果；用（待测）只标**尚未测量的线上指标**，禁止用（待测）代替机制。

允许嵌套：一级是支柱标题，二级补痛点 / 机制 / 约束。面试官应能只看一级列出 4～6 个追问钩子。

压缩正例（结构示范，领域可替换；完整项目级对照见样例库）：

> 把首页从整页 CSR 改为 Streaming SSR：聚合数据先做契约校验，不合法则降级 CSR，避免渲染脏数据；水合成功率单独观测。

> 把限流、幂等、库存预扣从下单主函数拆成分层：入口按用户限流 + 请求级幂等键 + 原子预扣。P95 目标明确；关键依赖不可用时软降级，靠对账兜底超卖。

槽位填法：`把 {旧方案} 收成 {新机制}：{怎么做}。约束 {数字}。结果 {主路径/调用方看到什么}`。

## Few-shot 生成流程与硬检查

规则描述“必须满足什么”，few-shot 用于对齐“成稿应该长什么样”。生成时不得直接复述金样或把技术名词堆成简历风格，必须按以下顺序执行：

1. **支柱抽取**：从项目演进、核心失败模式、系统机制和关键约束中选 4～6 个候选支柱；局部控件、单个接口和单文件改动默认下沉到追问。
2. **事实归档**：按 [仓库探索与证据归档](repository-investigation.md) 追踪链路；每个支柱先记录「核心矛盾、已实现机制、约束、结果、证据、进阶方案」。目标模式不以个人职责证据筛选；指标与已实现能力仍须有依据。
3. **Few-shot 对齐**：对照 [bullet-few-shots.md](../examples/bullet-few-shots.md) 的正例、反例和改写对照，学习因果链，不复制其中的项目名、数字、领域名词或场景。
4. **成稿**：首句交代问题/演进；随后说明机制、边界和结果。每条只表达一个支柱，结果必须紧跟机制。
5. **逐条质检**：每条至少有「问题或演进 + 机制 + 结果」；关键支柱尽量四槽齐全；能自然导出一个关于动机、权衡、边界或验证方式的主问。

以下句式不算结果，必须改写为可验证的架构结果或测量计划：`提升性能`、`提高稳定性`、`优化体验`、`增强可维护性`、`降低成本`。真实数字只能来自用户材料、仓库或明确测量；没有数字时不要为了模仿 few-shot 编造数字。

## 反例（禁止的简历调性）

写成下面这样就是**功能工单型**，即使每句都真实也不通过：

> - 接入某某列表刷新：处理两类竞态，成功率（待测）。
> - 开发某某确认弹窗：未知版本降级为纯文本。
> - 把渲染做成节流 / 截断，卡顿（待测）。
> - 接入某某开关与权限门控。

失败特征（按形态识别）：没有痛点或演进；海拔停在交互细节；结果用（待测）顶上；面试官无法从 bullet 问出「为什么是这种结构、约束怎么来的」。这些内容可以出现在对应支柱的**追问口播**里，不能当一级简历。

项目级失败对照（同一仓库被写成工单清单）见 [excellent-resumes/](../excellent-resumes/README.md) 各金样文末，不要把那里的专有名词带回本文件当规则。

## 名词分层

| 位置 | 允许 | 禁止 |
|------|------|------|
| 简历简介 + 一级/二级 bullet | 外部可检索的范式名（SSR、幂等、中间件、熔断、配额、隔离……以**本项目领域**为准） | 私有函数名、文件路径、issue 号、私有枚举、打点事件名、灰度开关键 |
| 口播正文 | 通用工程语言为主；黑名单私名每题有次数预算，且必须翻译 | 私名堆叠型（见 `oral-style-samples.md`） |
| 源码证据索引 | 函数名、路径、内部符号 | （此处集中存放即可） |

判断「业界可检索」：外部面试官用该词能搜到论文 / 框架 / 工程实践，而不是只能在本仓库 grep 到。公开 API / 标准协议可以留在简历；仓库私有函数必须下沉到索引。

## 出题契约

以[问题与回答契约](star-framework.md)为准：先写目标简介与 bullet，再抽取可见主张和触发词，只根据简历拟主问；追问根据简历和前序回答递进，答案由课程和源码支撑。

每个主问记录对应 B、触发依据、考查目标和 C 课程链接。检查题目能否由简历自然引出、答案是否正面回答、追问是否提前使用未知事实；不要靠补标签掩盖脱节。
