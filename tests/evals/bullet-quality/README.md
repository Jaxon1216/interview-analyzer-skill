# Bullet 选材与成稿评测

本组为独立生成与人工语义审读用例，不由 `npm test` 调用大模型。旧术语评测保持原样；本组不预先裁剪 DeerFlow 的事实或指定支柱、条数和用词。

- `deerflow-request.md`：真实本机仓库的完整分析范围，源码只读、按需查证，仅生成简介与 bullet。
- `edgemetric-request.md`：不同领域的简短合成材料，事实未按支柱分组；没有源码、指标或个人经历。
- `genbi-backend-request.md`：GenBI 后端的真实源码回归请求，复现只讲实现流程的成稿问题；`${GENBI_ROOT}` 指向只读项目仓库，`${OUTPUT_DIR}` 指向独立交付目录。自行选材，不给生成者旧 bullet 或诊断。

生成者仅获得冻结 Skill（含其原有引用）、仓库或原始材料与请求，不获得下面的审读标准、旧输出、预期答案或本轮诊断。保存第一次完整输出；后续修订另存，注明规则是否变化、是重新生成还是编辑修订。

分别记录以下判定，不合并成一个“通过”：

| 维度 | 审读问题 |
| --- | --- |
| 整组选材 | 能解释项目主要任务怎样完成吗？核心职责与系统机制是否进入主稿？材料分组、接口或权限检查是否取代了核心机制？ |
| 标题辨识度 | 目标领域同行能否识别具体设计？名称是否被正文的实际机制支持？接受准确同义表达，不要求金样标题。 |
| 设计动机 | 不看源码能否理解为什么需要该设计，具体应对什么使用需求、工程约束或风险？动机是否与做法对应，而非让读者自行猜测或只补一句“为提升稳定性”？ |
| 运行机制 | 能否读懂谁负责什么、如何协作、哪个条件改变行为？关键实现是否保留，而非只剩架构大词或源码动作清单？ |
| 具体变化与边界 | 能否指出用户、调用方或系统可见的具体能力与行为变化，且由机制支持？边界是否精确，目的是否冒充实测结果？是否重复条件、使用空泛尾句或强行补收益？ |
| 事实 | 源码或材料是否支持所有主张？有无借用金样身份、历史、层数、数字或技术组合？ |
| 技术栈与术语（单独） | 项目简介下是否以一行核心技术组合概括实现路线，而非版本、客户端包、标准库 API 或配置全集的盘点？摘要是否只含已核实且属于本次范围的技术？正文里的关键框架、库、协议和通用机制是否参与解释，还是被泛化成普通动作？名称准确，中英文自然，不因中文替代词删除真实技术，也不靠数量堆砌或补造技术。 |
| 可追问性 | 主问能否从成稿自然引出设计动机、运行机制、取舍或边界？无需输出完整面经。 |

成稿判定包括整组选材与逐条语言；术语合格不能抵消前者缺陷。单次生成仅说明本次行为，不能证明稳定优于旧版。内容审读与自动结构回归分开报告。

动机可以在开头、条件、作用或真实前后变化中表达，不按“针对”“由于”等字样评分，也不要求独立的背景句或固定 STAR 顺序。可结合 `../business-narrative.json` 的 E4/E6 检查当前机制下的目的分析与历史边界，结合 E5 检查真实痛点不会被一概删除。`npm test` 不执行这些生成与语义审读。
