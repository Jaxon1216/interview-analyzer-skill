## F1：日志缺失不统一触发 gap 与 durable reload

**状态：需修订；影响恢复失败边界，不推翻其余机制。**

当前 C07 第 43 行写：“游标太旧或日志不存在，服务端用无事件 ID 的 gap 控制帧说明需要 durable state”。面经 Q6 第 181 行又概括为“如果缓冲已淘汰，后端明确发送 gap”。这会使读者认为断线后任意日志缺失都会进入自动读持久状态和有界 rejoin。

原始源码保留了不同路径：

- `backend/app/gateway/services.py:2597` 的 `emit_gap_on_missing_stream` 默认为 False；`:2613`–`:2638` 明确说明并实现：终态 run 的 stream 丢失时，普通 join/stateless 调用返回 `end`，仅本次 thread-scoped 创建重试复用已有运行记录时，才按显式参数发 `gap`。
- `backend/app/gateway/routers/thread_runs.py:1031` 由本次 `record.idempotency_reused` 决定上述参数；`:1338`–`:1344` 的普通 join 还可能在 store-only 且 bridge 不支持跨进程时返回 409，否则按默认参数消费流。
- `frontend/src/core/api/api-client.ts:364`–`:374` 只有实际读到 `gap` 才进入 durable reload；普通 `end` 不触发这条恢复循环。服务端从 bridge 收到 `StreamGap` 时发 gap 的路径在 `services.py:2649`–`:2662`。

这些路径都属于本次“任务执行到结果展示”的范围。无需扩展其他业务，但应区分有保留日志时的游标越界、终态丢流的普通观察、幂等创建重试丢流和不可本地观察，不能统一承诺自动恢复。

### C05 HTML：事实与教学合格

学习成果具体：判断某次执行结束时可否释放共享 client。页面从未 acquire 的 S 开始，逐步加入 lead、child，再移除，图中同一个 S、连接、holder 集合和 release 计数持续演进。移除第一方时留下另一条实线，能直观看出为何不能释放；图旁反馈同时说明事件、适用规则与结果。换成 child 先结束只改变顺序，不变量保持，页尾将过程提炼成可迁移的判定步骤。

### C06 HTML：事实与教学合格
