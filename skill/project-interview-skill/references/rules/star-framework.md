# 面试问题、递进追问与回答契约

## 从主张出题

先完成简介与目标 bullet，按出现顺序编号 B1…；对每条拆出可见主张：问题、采用机制、关键约束与效果。主问阶段只依据这些文字，不从代码缺陷列表倒推出题。

填 `简历 → 面试展开` 表：`支柱 ID / bullet 标题 / 简历触发词 / 面试官主问 / 题号 / 核心课程`。触发词引用实际简历措辞，不能只填宽泛主题名。主问 Q1…一般每个支柱至少一道，也允许一道覆盖多条；每条支柱至少有一组 Q&A 和一节核心课程。

每个主问注明：

- **对应支柱**：B 编号；简介级题写“简介”。
- **触发依据**：简历中的具体词句；简介级题同样要有钩子。
- **考查目标**：希望确认的具体能力，例如幂等边界，而非泛写“技术深度”。
- **学习入口**：已展开的 C 编号课程链接。

主问通常 4～10 道，按实际主张调整；追问不计入总数。每组建议 2～4 个递进追问，按内容取舍，不为固定数量拆题。可加少量简介级问题，但不生成脱离项目的基础题库。

## 追问依据对话递进

面试官知道的信息随对话增加：主问只能用简历，追问可用简历和前面已经说出口的回答。给每个追问写一条短“触发依据”，引用其上游可见表述；连续追问时指明来自哪段回答。

常见递进：机制怎么工作 → 为什么不用另一方案 → 失败或并发时是否成立 → 如何验证与演进。根据具体答案选择，不要求每组套齐全部类别。若答案首次引入另一机制，追问可以沿它展开，但不能突然跳到未介绍的业务。

例：

> B1：后端组装博客作者与当前用户点赞态，前端直接消费完整列表。
> 主问：为什么把列表信息组装放在后端？
> 回答先说明多数据源聚合，再说明当前查询方式。
> 追问：你刚说逐条补充作者与点赞态，会不会形成 N+1？
> 回答说明批量化方案后，可继续问怎样验证查询次数和响应耗时。

此时直接问“Feed 游标怎样不重不漏”缺少对话依据。要么把 Feed 设为独立支柱，要么先自然介绍它，再追问。

题干不出现仓库路径、私有函数、issue 或面试官未知的开关。即使去掉这些名称，仍需检查题目的前提是否从简历或回答可知。公开 API、协议和算法名可以使用。

## 回答按题型组织

| 题型 | 结构 | 检查重点 |
| --- | --- | --- |
| 项目方案/经历 | 场景与目标 → 动作和权衡 → 结果（可用 STAR） | 机制与结果有因果关系 |
| 技术原理 | 先直接结论 → 原理 → 项目例子 → 边界 | 开头真正回答问题 |
| 故障定位 | 现象 → 假设 → 定位证据 → 修复 → 验证 | 真实记录与假设排障分清 |
| 设计演进 | 当前限制 → 候选方案 → 选择依据 → 验证方法 | 未实现部分用方案语气 |

项目口播用第一人称，概念题可以直接解释技术。主问可按 60～90 秒的表达深度准备，追问随复杂度调整；**不设统一最低字数，不强制每道题完整 STAR**。不要用“待测、尚未验证、不是我写的”等重复背景凑篇幅。验证状态在对应位置说清即可。

## 最后用面试官视角复审

只看最终简介、bullet 和前序回答，逐题检查：

1. 是否能指出触发这道题的原句？这句话真的足以引出该题的前提吗？
2. 题目是在验证具体主张，还是泛泛问“怎么优化”？
3. 回答开头是否正面回应？机制、取舍和例子是否支撑本条主张？
4. 关键主张是否漏问，例如声称异步下单却只问事务 API？
5. 课程是否真正讲过答案所依赖的机制？相同知识只链接，不重复抄整课。

关联弱时重写或合并题目，不能只补一个 B 标签掩盖脱节。重要性可标“核心/深入/拓展”并给依据，不把所有题都标成有统计根据的“高频”。
