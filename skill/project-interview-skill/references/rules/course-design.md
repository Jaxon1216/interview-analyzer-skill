# 源码课程设计与质量分层

## 默认学习者与选题

默认读者懂基础语法、用过框架、能写 CRUD，当前目标是看懂完整项目、修改关键机制并讲清取舍。用户明确初学或资深时调整解释深度。

先确定方向与真实覆盖范围，再按场景编排课程。前端/后端通常 6～8 课，全栈通常 8～12 课；这些是规模参考，不是凑数要求。每课围绕一个可从触发走到结果的场景；机制过于独立、前置依赖不同或一课跨度过大时拆分。一个源文件可支撑多课，一课也可以跨多个文件，不按源码文件数拆课。

默认总览与所有核心课程本次完成；可选课只列主题、价值、前置条件和展开入口，不创建占位文件。用户只要大纲或指定课时才缩小交付。大型仓库选代表性主链，明确覆盖范围，不假称讲完所有模块。

## 内容重心：维度用于查漏，场景用于成课

| 维度 | 默认投入参考 | 前端示例 | 后端示例 |
| --- | --- | --- | --- |
| 项目地图与运行入口 | 10% | 页面、路由、开发服务和代理 | 启动、配置、依赖绑定和请求入口 |
| 核心链路与数据流 | 30% | 事件→请求→状态→渲染 | 参数→业务→存储→响应 |
| 特色机制与运行原理 | 30% | 响应式、异步竞态、生命周期、资源清理 | 并发、事务、缓存、异步消费 |
| 工程质量与排障 | 20% | 调试、测试、性能、安全、可访问性 | 测试、观测、性能、安全、部署 |
| 设计取舍与演进 | 10% | 状态归属、组件边界、替代设计 | 一致性、容量、恢复、替代架构 |

比例用于判断是否偏题，不要求统计字数。基础讲解总体约不超过一成，按实际阻塞点穿插，不为八类知识各写一章通识教材。

按项目查漏：

- 前端：框架/类型建模、数据所有权、路由与会话、请求取消和竞态、加载/空/错状态、表单、浏览器与网络、构建、测试调试、性能、安全、可访问性与资源清理。
- 后端：语言与标准库惯用法、请求生命周期、超时取消、并发协作、连接池、数据建模/索引/事务、缓存、消息/幂等/重试/背压、观测、测试、安全、部署回滚。
- 全栈：重点讲边界契约与两端协作，不重复复制两套课程；按实际仓库比重安排，不强求 50:50。
- 非当前技术栈只作有价值的进阶：JS 项目不强制 TypeScript 主课，无 K8s 配置不编造编排链路。运行时只深入到解释当前问题所需的程度，调度器或 GC 源码可放选读。

## 学习分层

每课标明“核心”或“选读”，再说明预期掌握层次；课程性质和掌握层次是两个不同维度。

1. **看懂**：能复述输入、输出、状态变化和模块职责。
2. **验证与修改**：能定位关键代码、解释机制、执行或设计小实验，知道结果为什么变化。
3. **设计与表达**：能比较替代方案、分析失败边界，并回答对应面试题。

核心课至少讲清前两层；简历重点支柱讲到第三层。层次加深必须增加因果、实验或取舍，不能只增加术语。

## 单课内容

使用 C01…稳定编号，文件名与课程标题带编号。每课包含以下内容，可合并相邻段落，但不能用清单替代讲解：

1. **课程导航**：返回主导学、前置课程、建议下一课、相关 B/Q 链接与目标。标明 `课程性质：核心` 或 `课程性质：选读`。
2. **场景与预测**：具体输入或用户操作、期望结果；先让读者预测状态/数据会如何变化。
3. **主链与职责**：一张简洁流程图或文本链，讲清同步调用、事件/队列、状态所有者与跨层契约。
4. **源码阅读**：按执行顺序给出路径、符号、阅读目的与下一步。随后解释关键代码为何产生对应行为，而非只列文件名。
5. **机制与边界**：结合具体输入输出解释核心原理、异常路径、并发或生命周期问题；区分当前实现与分析推断。
6. **动手验证**：前提、操作或命令、预期观察、失败时检查位置。没有实际执行就称为验证任务，不写成已通过；课程生成不等于自动修改业务代码或启动全部基础设施。
7. **理解与表达**：通常 2～4 道题，覆盖推演、定位和取舍；参考答案/提示可用折叠块放在题后。链接相关面试题，避免重复口播全文。

## 代码引用与可移植性

生成文档使用相对 Markdown 文件链接，符号名作主要定位，行号作辅助文字；按课程文件所在目录计算路径，不能照抄仓库根相对路径当可点击链接。主导学和面经使用相同规则。

关键片段按解释需要引用，一般每课少量短片段足够；保留必要上下文，不粘贴整文件。伪代码明确标为简化模型，不能冒充仓库实现。框架、库版本从项目依赖读取，API 不确定时查对应官方文档。

编辑器专属跳转只是增强，不是交付依赖。课程靠路径、符号、片段与阅读顺序即可使用；Markdown 锚点可辅助导航，源文件行锚点不保证所有客户端支持。

## 更新与质量检查

- 主导学链接每节核心课；课程反向链接主导学与相关面经。B/Q/C 编号在更新时尽量稳定，新增用新编号，不重排用户学习记录。
- 用户笔记、完成状态和已写答案保留；只更新受代码或目标变化影响的章节及关联。
- 每课至少能检查：因果讲清了吗？代码落点可定位吗？验证可以操作吗？预期与异常可区分吗？能支撑相关 bullet 与 Q&A 吗？
- 找到机制 bug 要解释它对链路的影响，并给修复/验证练习；不要让缺陷清单取代正常机制教学。
- 避免重复背景、泛泛概念、全课文件清单及“请继续问 AI”代替正文；不靠课程数、字数或标题齐全宣称内容优质。
