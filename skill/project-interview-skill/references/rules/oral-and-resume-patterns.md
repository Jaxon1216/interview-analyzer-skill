# 口播叙述与简历（抽象模板）

本文件是**可移植规则**，适用于任意项目 / 岗位。写简历 bullet 前默认打开[酥神 bullet 模板](../excellent-resumes/susu-bullet-template.md)，按需再读 [excellent-resumes/](../excellent-resumes/README.md) 的项目级金样；**不要**把金样里的产品名、层名、数字抄进用户项目。生成 bullet 时同时对照领域中立的 [bullet few-shot](../examples/bullet-few-shots.md)，只学习结构，不复制素材。

## 回答组织

回答先回应问题，再解释机制、项目例子和边界。项目方案题可用 STAR；原理、故障、演进题按[问题契约](star-framework.md)选择结构，不统一设最低字数或强制重讲背景。

目标模式的项目示范用第一人称，供学习掌握后使用；概念解释可直接说技术。文首说明一次目标定位，不把职责或测量免责声明重复塞进每题。内部私名少量使用并解释，具体定位下沉到源码索引。

---

## 简历「项目简介 / 一句话」写法

用 **1～2 句** 说清：**做什么 + 关键技术/形态 + 可选一句价值**，避免形容词堆砌。

**抽象公式**：

> 基于 {核心技术栈/范式} 的 {产品形态}，用户/业务侧能 {核心操作}，系统支持 {关键能力 A、B}，{可选：差异点如同步/异步、端侧等}。

**示例形态（勿照抄项目名）**：

> 基于 AI 大模型的智能 BI：用户上传 Excel 后，AI 自动生成 ECharts 图表与分析结论，支持同步/异步生成与拖拽看板组合多图。

面经文档中的 **项目概要** 必须接近此密度与信息量，可直接贴简历「项目描述」栏。有真实 star / 奖项可以写；没有就省略，禁止编造。

## 先定简历海拔（写 bullet 的第一步）

先按项目目标组织候选，说明机制解决的障碍及对应结果维度，再比较技术深度：**架构演进 > 系统机制 > 交互 / 实现细节**。同一业务问题下的功能可合并为支柱；缺少业务材料时按已知工程目标组织，不编造增长目标。

| 海拔 | 形态（按形态识别，不锁项目） | 默认去向 |
|------|------------------------------|----------|
| 架构演进 | 旧形态 → 新形态：固定流程变为可编排；逻辑散落变为可扩展分层 | 一级支柱 |
| 系统机制 | 状态/一致性、隔离、预算、降级、扩展点、契约 | 一级，或该支柱的二级 |
| 交互 / 实现细节 | 某一控件、某一协议字段、某一文件的读写、某一布局约束 | **追问**，不进一级 bullet |

- **求职方向只调口播侧重点，不改变简历海拔。** 不要把系统机制降成该方向上的功能清单（前端写成页面交互列表、后端写成 CRUD 列表、AI 写成调了某个模型）。优先写值得掌握的架构支柱，再按方向讲清链路上的落点。
- 贡献模式且用户明确只做子模块时：一级 bullet 仍写**该模块**的机制与约束；不要把局部改动扩成全仓 owner，也不要把全仓边角堆成多条工单。
- **禁止**把导学「重点亮点与学习顺序」原样粘成简历 bullet。导学是读代码地图，简历是面试官 30 秒能追问的支柱。

目标模式按仓库机制写有力度的目标表达，不因缺少作者证据退成修复清单；不主动审计作者。用户明确参与的内容在含金量相近时优先。

用户要求只整理实际贡献时，按其说明选择职责动词；局部参与写清模块边界，不需要扩大到全仓。默认目标模式与贡献模式不要混用规则。

## 简历 bullet 成稿方式

一级通常 4～6 条，按项目实际机制选取；每条以 `- **具体支柱名：** 正文` 独立成行。标题点名具体机制，保留必要的通用技术词，避免将“治理、体系、建设”当作技术内容。

默认对照[酥神模板](../excellent-resumes/susu-bullet-template.md)的原文语言：直接写动作与运行方式，关键约束放在对应步骤，效果紧随机制；有真实演进才交代旧→新。背景可在项目层共用，不要求每条都以“针对……的问题”起笔。

问题、机制、约束、结果用于事实查漏，不是成稿必须填满的四槽。没有旧架构证据就直接讲当前机制；没有性能数据就写源码能支持的具体效果。不得用待测尾注或测量计划结束简历条目，指标缺口另放证据记录或相关回答。

简单机制用紧凑分句；复杂支柱可以有 2～4 条二级说明，按子机制分层，不挤成包含全部调用节点与技术栈的长句。约束必须相关，不为补数字混入停机、部署等另一主题。

## Few-shot 对齐与审读

1. **支柱抽取**：选出值得展开的架构或系统机制，局部控件、单个接口和单文件改动通常下沉到追问。
2. **事实归档**：按[仓库探索](repository-investigation.md)记录目标、已实现机制、边界、具体效果与证据，核对指标口径和归属；历史演进有依据才写，未实现方案另列。目标模式不以个人职责证据筛选。
3. **语言对齐**：读默认金样原文与[领域中立 few-shot](../examples/bullet-few-shots.md)，学习具体动词、因果和分层方式，不迁移项目素材。
4. **成稿**：围绕一个支柱直接说明怎么做、为什么产生该效果；背景与约束按需要自然插入，不逐条套同一开头。
5. **审读**：检查标题是否具体、机制是否能复述、约束是否相关、效果是否成立、是否需要拆成二级；能否自然引出设计动机、运行方式或边界的主问。

“提升性能、提高稳定性、优化体验、增强可维护性、降低成本”不能单独充当结果。改成有因果的具体变化或真实指标；无法支持的收益直接删除，测量计划不进入简历正文。私有函数、文件路径与内部枚举进入源码证据索引，标准协议与公开技术名可保留。

## 反例（禁止的简历调性）

写成下面这样就是**功能工单型**，即使每句都真实也不通过：

> - 接入某某列表刷新：处理两类竞态，成功率（待测）。
> - 开发某某确认弹窗：未知版本降级为纯文本。
> - 把渲染做成节流 / 截断，卡顿（待测）。
> - 接入某某开关与权限门控。

失败特征（按形态识别）：没有解释机制；海拔停在交互细节；结果用（待测）顶上；面试官无法从 bullet 问出「为什么是这种结构、约束怎么来的」。这些内容可以出现在对应支柱的**追问口播**里，不能当一级简历。

项目级失败对照（同一仓库被写成工单清单）见 [excellent-resumes/](../excellent-resumes/README.md) 各金样文末，不要把那里的专有名词带回本文件当规则。

## 名词分层

| 位置 | 允许 | 禁止 |
|------|------|------|
| 简历简介 + 一级/二级 bullet | 外部可检索的范式名（SSR、幂等、中间件、熔断、配额、隔离……以**本项目领域**为准） | 私有函数名、文件路径、issue 号、私有枚举、打点事件名、灰度开关键 |
| 口播正文 | 通用工程语言为主；黑名单私名每题有次数预算，且必须翻译 | 私名堆叠型（见 `oral-style-samples.md`） |
| 源码证据索引 | 函数名、路径、内部符号 | （此处集中存放即可） |

判断「业界可检索」：外部面试官用该词能搜到论文 / 框架 / 工程实践，而不是只能在本仓库 grep 到。公开 API / 标准协议可以留在简历；仓库私有函数必须下沉到索引。

## 出题契约

以[问题与回答契约](star-framework.md)为准：先写目标简介与 bullet，再抽取可见主张和触发词，只根据简历拟主问；追问根据简历和前序回答递进，答案由课程和源码支撑。

每个主问记录对应 B、触发依据、考查目标和 C 课程链接。检查题目能否由简历自然引出、答案是否正面回答、追问是否提前使用未知事实；不要靠补标签掩盖脱节。
