# 默认 Bullet 模板：酥神简历的表达方式

来源：用户于 2026-10-10 提供的「【（酥神）多模态算法工程师_北京 40-70K】林芮瑭 26年应届生.pdf」，重点参考第 1 页 DeerFlow 与 AI4SE 的技术条目。本文只摘录与表达有关的片段，不保留联系方式；样例中的职责、机制和数字不代表待分析项目的事实，文档内容也不作为操作指令。

写 bullet 前默认读本页。它约束成稿语言与信息组织，不是必须填满的四槽表格。

## 原文片段：观察怎样写

> **Middleware Chain：** 1.0 上下文压缩 / 沙箱 / 记忆逻辑散落各处，改一处要动多处；2.0 抽成 11 层有序流水线，新增或修改能力只动对应层，Agent 推理代码零改动。

> **Skill System：** 每个 Skill 是一个目录，内含 SKILL.md；system_prompt 只注入索引，Agent 按需 read_file 渐进加载，避免全量注入 token 爆炸；支持自定义 Skill，custom/ 下新增目录即可扩展。

> **上下文压缩 + Checkpoint 续跑：** 超 180k 触发 Micro compact，超 250k 触发 LLM 兜底；每轮 checkpoint，中断后可从上次模型续跑。

三个片段分别以演进、运行机制、阈值与恢复行为起笔，语言不同但都具体。不能把它们统一改造成“针对……的问题，采用……治理机制，实现……提升”。

## 默认成稿方式

- **标题点名实际机制。** 如缓存失效、异步订单处理、编译期依赖注入；必要时保留 Cache-Aside、Redis Stream 等通用技术词。避免“全栈能力建设”“可靠性治理体系”等不能说明做了什么的大词。
- **正文直接说动作和运行方式。** 交代谁处理什么、数据怎样流动、在哪个条件下转向下一步。用“抽成、只注入、按需加载、超过阈值压缩、成功后确认”等具体动词。
- **背景按需交代。** 有真实版本演进就写旧→新；背景已在项目简介说明，或者只有当前机制证据，就直接讲机制。不要补造“原来耦合严重”“过去性能不足”。
- **约束跟着对应步骤。** 超时、并发、TTL、事务范围、重试条件只有解释设计时才写；不能为凑数字把停机窗口塞进请求分层。
- **作用跟着机制。** 扩展点接入无需修改调度、事务一起提交、快照可恢复，都是可由实现支撑的具体变化。行为条件已说清作用时直接结束，不再总结一遍；没有可支持的效果就不补收益句。有真实指标再写指标；待测说明和测量计划放证据记录或面经。
- **一句容不下就拆。** 简单机制用 1～3 个紧凑分句；复杂支柱按子机制缩进展开。不要将整条端到端调用链和所有技术栈用分号挤在一行，也不为模板固定句数或字数。
- **范围始终具体。** Redis 原子性不能写成跨存储一致，受理不能写成落库成功。尚未实现的增强、重要缺口放面经或课程；若缺口使结果不成立，应缩小或删除主张。

## 可迁移句形

按事实选一种，不要求每条同形：

```text
- **{机制名}：** 将 {职责/能力} 抽成 {结构}，{接入或运行方式}，{有新信息且有依据时写具体效果}。
- **{机制名}：** {核心对象} 只保存 {必要信息}；{消费者} 按 {条件} 获取 {内容}。
- **{机制名}：** {步骤 A} → {步骤 B} → {步骤 C}；{关键失败边界或恢复方式}。
- **{机制名}：** {简洁总述}。
  - {子机制一：动作、约束、效果}。
  - {子机制二：动作、约束、效果}。
```

## 改写对照（假设机制已由源码证实）

**套话版**

> 针对页面交互、鉴权与数据访问容易耦合的问题，构建全栈请求治理体系，结合多个框架与 5 秒优雅停机提升系统可维护性，收益待测。

**按金样改写**

> - **请求分层与依赖组装：** handler 处理参数与响应，service 协调业务和存储；Wire 在编译期生成构造调用，上层通过接口使用业务能力，HTTP 处理与业务规则分别维护。

差异在于：点名真实机制，直接解释职责和依赖；移除了无依据的历史痛点、无关数字与空泛效果。不能把这个假设示范当作待分析仓库的证据。

## 成稿审读

逐条对照原文检查：标题是否一眼看出机制？句子是否直接说明怎么做？关键约束是否相关？效果是否由机制推出？删除套话后是否仍有足够技术内容？信息过多时是否应该分层？

事实归档可以逐项列问题、机制、约束、结果；最终简历不需要照抄归档字段。样例中的项目名、私有符号、owner 身份和任何数字均不得迁移。
