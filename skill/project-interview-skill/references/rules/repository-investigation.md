# 仓库探索与机制归档

探索用于识别值得学、值得讲的项目机制。默认目标简历模式不审核个人贡献，不主动检查 commit author；用户提供的参与经历可用于同等含金量下的排序。仅用户明确要求实际贡献材料时，按其说明限制范围。

## 范围与入口

- 确认项目根目录、语言、框架、入口、配置和部署方式，区分业务源码、生成代码、依赖、示例与测试。
- README 用于理解目标，源码用于确认行为；不要仅凭目录名或文档宣传抽取支柱。
- 默认全栈覆盖仓库中实际存在的前后端，不意味着各占一半；无前端源码时只讲调用端契约。
- 记录当前源码基线或分析日期与模块范围，帮助日后更新课程；无需统计作者或寻找个人改动证明。

## 沿场景追踪

先追踪 2～4 条代表性链路，再按支柱和课程需要补查。包括启动与依赖绑定、请求/事件入口、数据与状态变化、异步消费或回调、对外结果及资源清理。异步目标要追到注册、投递与消费位置，不能仅因函数名相似就认定调用关系。

每条链路回答：

1. **问题**：当前机制解决什么矛盾？没有演进证据时直接解释当前问题，不虚构旧架构或事故。
2. **机制**：输入输出、关键状态、模块职责与实际调用顺序是什么？
3. **边界**：哪里会超时、竞态、不一致、重复执行或资源泄漏？实现了哪些处理，还有哪些限制？
4. **效果与验证**：实现、测试、配置和运行结果分别能证明什么？代码可见的结构效果与性能实测分开。

候选支柱事实卡：`问题 | 已实现机制 | 约束/失败边界 | 具体效果 | 源码/测试/配置位置 | 验证状态 | 进阶方案 | 用户明确参与（可空）`。

## 选材与课程落点

优先能解释动机、替代方案、失败处理和验证方法的机制。架构、跨模块约束与系统机制优先于单点工单；近期修复可以作为其下的实现案例，不应挤掉项目核心能力。

仓库已有但用户尚未学会的机制可以进入目标 bullet，必须配套核心课程。未实现增强列作进阶目标，不因理想方案更完整就把它混入现状。找到 bug 时准确说明影响，在对应课讲解或设计修复实验；不把整个面经改成代码审计报告，也不自动修改业务代码。

只有用户描述时注明资料范围，路径、符号、实验结果无法核验就说明缺口。缺少指标时用具体机制效果，不反复追问线上数据后才出稿。真正影响选材的问题集中询问，其他内容先完成。
